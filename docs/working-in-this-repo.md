# Working in this repo: the explanations behind CLAUDE.md

CLAUDE.md holds the rules, short, because every session loads it on every call. This file is what it was before October 11, 2026's slimming: each rule with how it works, why, the files involved and examples. Where it says "this file", it means CLAUDE.md. The rules in CLAUDE.md win where the two differ.

## Index

**Summary:** Claude Code loads this file into every session in this repo, and its rules are followed as instructions. Hate Watch has two parts. The app is in `app/` (Expo, see `app/CLAUDE.md` and `app/AGENTS.md`). The server is in `server/` (Node, SQLite, Fly.io). `README.md` explains how everything works. Each section below gives its rules first, plainly. The explanation, the files involved and examples come after each rule. Those explanations describe how things work and why. They add no rules of their own.

**Sections:**
- **Read the docs first**: before planning or changing anything, read the docs for that area and name them in the plan. A change that departs from the docs updates them in the same change. This section maps each area to its docs: the README headings, the duplicate-alert doc, the module header comments, the Obsidian vault, and the hook that enforces the rule. It also sets how docs are kept: every change updates its docs in the same commit, and every document opens with an index with the full detail below it; a second hook checks both on every commit.
- **Release flow**: ask before every commit, push or deploy. It also covers deploying the server to Fly and backing up production data first (and the Litestream replica and the `/health/deep` monitor check, which docs/redundancy.md details), the server switches for ESPN's clips and images, developer notices, TestFlight builds, the checks before a build, over-the-air updates, the league display that comes from the server, and EAS's free-tier queue and Apple's upload errors.
- **Don't run npx expo lint in app/**: why `expo lint` broke an iOS build. Typecheck with `npx tsc --noEmit` only, check the lockfile with npm 10 before a build, and install with `npm ci`.
- **Patch notes**: `PATCH_NOTES.md` gets every shipped change under "Next build". The heading is renamed when a TestFlight build goes out. Each section stays under 4,000 characters and uses no emoji, because it is pasted into TestFlight's "What to Test".
- **Two machines (Windows and Mac)**: setting up a machine (`claude-config/install.sh`, `npm ci`), the logins each machine needs (GitHub takes a personal access token), what each machine keeps outside git, and the Mac's game recorders.

**Where things are:**
- The app: `app/` (Expo SDK 57). `app/eas.json` holds the build profiles, `app/app.json` the app config, and `app/package.json` the `update` script.
- The server: `server/`. The Fly config is `server/fly.toml`, the image is `server/Dockerfile`, and the switches are `server/src/flags.ts` (with `server/src/flag-cli.ts`). Developer notices are `server/src/notices.ts` and `server/src/notice-cli.ts`.
- The release history: `PATCH_NOTES.md`. Store releases: `docs/` (`docs/android-release.md` for Google Play). How duplicate alerts are kept out: `docs/duplicate-alerts.md`.
- Claude Code's setup: `.claude/settings.json` (hooks), `.claude/hooks/require-docs.mjs` (the docs gate), `.claude/hooks/require-docs-update.mjs` (the commit check: docs updated, docs indexed), `.claude/hooks/remind-vault-log.mjs` (the vault-log reminder), and `claude-config/` (the user settings that `install.sh` copies onto each machine).

## Read the docs first
Before planning or changing anything (a feature, a fix, an alert, its wording, a release step), read what the docs say about that area, and say in your plan which sections you read. The code does what they describe: a change that departs from them updates them in the same change (the README section, `PATCH_NOTES.md`).

For example, a plan to change how a loss alert is worded names the README's "Notifications" section, and `docs/duplicate-alerts.md` because loss alerts are alert code. If the wording in the README's table changes, the README changes in the same commit, and `PATCH_NOTES.md` gets a line under "Next build".

- `README.md` is the reference for how everything works, and its headings are the map: Notifications (every league's alerts, the defaults, Settings), Real-time (polling, football play revisions), Data (rosters, images), Scores tab, Stats pages, Successful Hate Watch counter, Leaderboard, Startup guide, An alert on its own screen, Developer notices, Sharing an alert, Tests, Known limits. The UFC and college football are in `PATCH_NOTES.md` and their modules' header comments (`server/src/ufc.ts`, `cfb-poll.ts`).
  - The README's full headings are "Notifications (every alert type, all user-controllable)", "Real-time: how fast is it?", "Data: rosters, duplicates, and images", and so on. Release steps are under its "Deploy" heading ("Server → Fly.io", "iOS / Android → EAS", "App Store Connect answers", "Hate Watch Plus (the $5/month subscription)", "Icons and splash").
  - The README has no UFC section and no college football section. For those, the patch notes' "UFC" and "FOOTBALL" lists under "Next build" and the header comments of `server/src/ufc.ts` and `server/src/cfb-poll.ts` are the docs.
- This file for releasing: deploys, builds, over-the-air updates, patch notes, server switches, the two machines.
- `app/AGENTS.md` before touching any Expo or React Native API (fetch the versioned Expo docs), and `docs/` for store releases.
  - Expo changes its APIs with every SDK, so the docs to read are the ones for the SDK the app is on (`expo` is `~57.0.x` in `app/package.json`), not what is remembered.
  - `docs/android-release.md` is the Google Play guide: an account, Firebase push, EAS builds, the store listing, the 12-tester closed test, and production.

Its "Files this covers" lists the alert files; the hook below blocks an edit to one until it has been read since the latest user message.
  - The hook's list of alert files (`ALERT_CODE` in `.claude/hooks/require-docs.mjs`) is: in `server/src/`, `detectors`, `live`, `fanout`, `revisions`, `event-types`, `push`, `f1`, `ufc`, `news`, `recap`, `cfb-poll`, `hate-watches`, `notices`, `clips`, `db` and `api` (each `.ts`); any file in `server/test/`; and `app/src/lib/store.tsx`.
  - What counts as a full read: the Read tool on the whole file (no offset, and either no limit or a limit of 400 lines or more); `cat`, `bat` or `less` of it in a shell; or an Obsidian MCP call that names the "Duplicate alert protection" note. A read only counts if it came after the latest user message, and it is never remembered between messages.
  - When the hook blocks, it names the file and says to read `docs/duplicate-alerts.md` in full again, then retry the edit.
- The module's own header comment: every file in `server/src` starts with what it does and why.
  - For example, `server/src/flags.ts` opens with what the switches are for and the two ways to turn one off. `server/src/notice-cli.ts` opens with every command it takes.
- On the Mac, the Hate Watch Obsidian vault (`~/Documents/obsidian/hate-watch`, start at `Home.md`) has all of this split by topic, with the game review reports and the standing decisions. It's a private copy; the repo wins where they differ. It rebuilds itself from GitHub's main (the README, this file, `PATCH_NOTES.md` and the commit log) when a session starts and after any git push, pull, fetch or merge (`.claude/settings.json`; nothing happens on a machine without it), so a change documented in the README is documented there too.
  - How the rebuild works: `.claude/settings.json` runs `~/Documents/obsidian/hate-watch/.tools/sync.sh` on SessionStart, and again after each Bash call (PostToolUse) with `--hook`. In hook mode the script exits at once unless the command contained `git push`, `git pull`, `git fetch` or `git merge`. Both hooks are async, with a 120-second timeout. If the script isn't there or isn't executable, the hook does nothing and still succeeds.
  - `sync.sh` fetches `origin/main`. It rebuilds only when main has moved since the last build (recorded in `.tools/last-built`), or when run with `--force`. The rebuild runs `.tools/build_vault.py`. Runs never overlap (a `.lock` folder, cleared after 10 minutes if a run died). Results go to `.tools/sync.log`, and a failed rebuild keeps the notes from the last good build.
  - The notes are built from main as it is on GitHub, so a change on a branch or in a worktree reaches the vault only after it is pushed to main.
  - The vault script cuts sections out of this file by their headings and by how some bullets begin: the bullets starting "- Server:", "- Server switches", "- App:", "- Before a build", "- App over the air", "- How the app shows each league" and "- EAS's free tier". If those headings or openings change, the vault build fails or loses a note.
- Side sessions and subagents follow the same rule: a brief names the docs to read first.
  - For example, a brief for a side session that changes MLB alerts names the README's "Notifications" section and `docs/duplicate-alerts.md`. A brief for a release task names this file's "Release flow".
- A hook enforces it (`.claude/settings.json` runs `.claude/hooks/require-docs.mjs`): an edit to `app/` or `server/` code (with the edit tools, or a shell command that writes to a code file; read-only commands pass) is blocked until the session has read `README.md`, `docs/`, an `AGENTS.md` or the vault, and the block says which docs cover that file. `HW_DOCS_GATE=off` in the environment turns it off for an emergency.
  - What it checks: Edit, Write, MultiEdit and NotebookEdit calls on a path under `app/` or `server/` in `src/`, `test/` or `scripts/`, but not `node_modules`. It also checks Bash commands that both name such a file and write to it. Writes include a Python or Node file write, `sed -i`, `perl -i`, a redirect (`>` or `>>`), `tee`, `cp`, `mv`, `git apply` and `patch`. Read-only commands such as `grep`, `sed -n` and `cat` pass.
  - What counts as having read the docs: any earlier tool call in the session (Read, Bash, Grep or Glob) whose input names `README.md`, a file in `docs/`, an `AGENTS.md`, a folder's `NOTES.md`, or the vault, or any call to an Obsidian MCP tool. Once that is found, a marker file in the temp folder (`hw-docs-read-<session id>`) means later edits in the session are not checked again. The stricter alert-code check above still runs on every edit.
  - When it blocks, the edit fails (exit code 2) and the message lists the docs for that file. For example, an edit to `server/src/flags.ts` points to this file's server switches bullet and the vault's "Feature switches" note. An edit to a file under `app/` also points to `app/AGENTS.md`. If no transcript can be found, the hook lets the edit through rather than block it blind.
- **Update the docs with every change, in the same commit.** Any change to the app, the server, an alert, a release step or the Claude setup updates every doc that describes it: the README section, the file in `docs/`, this file, the module's header comment, and `PATCH_NOTES.md` for a shipped change. On the Mac, also the vault: the day's log note (`80 Log/<date>`) lists the day's commits by itself (generated from git in `.tools/build_vault.py`, "Commits that day (generated)"; a day with commits and no hand-written note gets a bare one, and `sync.log` warns when that happens for the last three days), so the line to add is the story, as a bullet in that day's `note('80 Log/<date>', ...)` call, and any hand-written note in `.tools/build_vault.py` the change makes wrong (a decision, a review, a code map), then a rebuild. A new subject with no doc gets a new file in `docs/`.
  - For example, a new MLB alert updates its row in the README's alert table, its section in `docs/alerts.md`, `docs/duplicate-alerts.md` if it adds a kind of alert id, and `PATCH_NOTES.md`. A new release step updates this file and the README's "Deploy" section.
  - When nothing documented changed (a refactor, a comment, a test), the commit message says so, with a line `Docs-unchanged: <why>`.
- **Every document opens with an index, with the full detail below it.** This is the format of the README, this file and every file in `docs/`, and every new one follows it:
  - A file in `docs/` (and this file): `# Title`, an optional short intro, then `## Index` as the first `##` heading: a `**Summary:**` paragraph, then every `##` section of the file named with one line on what it holds. Then the sections.
  - The README: its `## Index` lists every `##` and `###` section with the first sentence of its summary, and every `##` and `###` section opens with a paragraph that starts `**In short:**` (2 to 4 sentences).
  - Below the index, as much as there is to say, with details and examples: every behavior, rule, threshold, default, setting, command, endpoint, file and function; why it is that way; edge cases; real examples from the code, the tests or the git log (real players, teams, games, dates and numbers). Check every claim against the current code and cite `path` and function names. Never write from memory: leave out what can't be confirmed.
  - When a section changes, its summary and its line in the index change with it. A new section gets a line in the index.
  - The vault needs nothing extra: `build_vault.py` gives every note its own index (its summary, then each section with its first sentence), and imports every file in `docs/` as a note.
- A second hook enforces both (`.claude/settings.json` runs `.claude/hooks/require-docs-update.mjs` before every Bash call, and it acts only on `git commit`): it stops a commit that changes code (`app/` or `server/` in `src/` or `scripts/`, `.claude/hooks/`, `.claude/settings.json`, `claude-config/`) without changing any doc (`README.md`, `CLAUDE.md`, a file in `docs/`, a `NOTES.md`) unless the message has a `Docs-unchanged:` line, and it stops a commit whose `README.md`, `CLAUDE.md` or `docs/*.md` breaks the format above.
  - What it checks in the format: `## Index` is the file's first `##` heading, every `##` heading is named in the index, and, in the README, every `##` and `###` section opens with `**In short:**`. Headings inside code blocks don't count. It reads the files as staged (as on disk with `git commit -a`).
  - What passes: a merge (`MERGE_HEAD`), a commit of tests or docs only, any Bash call that isn't a commit, and `HW_DOCS_GATE=off`. `PATCH_NOTES.md` on its own doesn't count as docs, because it's the release log, not the description.
  - When it stops a commit, it lists each problem. Fix it, stage it and commit again.
- A third hook records and reminds, after the fact (`.claude/settings.json` runs `.claude/hooks/remind-vault-log.mjs` after every Bash call, PostToolUse, which Claude Code fires only for a command that succeeded; one that exits non-zero never reaches it, and an interrupted one is skipped): once a command is a `git commit`, a `fly deploy` or `flyctl deploy`, an `eas build`, `eas update` or `eas submit` (with or without `npx`), or `npm run update`, it acts on the vault's log for the day.
  - Matching: quoted strings and heredoc bodies are dropped first and each command in a chain (`;`, `&&`, `||`, `|`) is checked from its start, so `grep "git commit" x`, a heredoc that mentions `flyctl deploy`, `eas build:view` and `--help` or `--dry-run` runs don't count, while `cd server && flyctl deploy --remote-only` and `npx eas-cli@latest build ...` do.
  - A deploy, build or update is recorded by itself: one JSON line (`ts`, `date`, `time`, `kind`, `head`, `cwd`, `command`) appended to `~/Documents/obsidian/hate-watch/.tools/events.jsonl`, which `build_vault.py` renders as "Deploys and builds that day (generated)" in that day's log note (a day with only such events gets a generated note too). The hook then starts `sync.sh --force` in the background, so the note updates at once. A commit is not recorded: the commit list is generated from `git log origin/main`, so it appears after the push and the rebuild.
  - Every match also adds a note to the session: the entry was (or will be) generated, and the story (what was decided, deployed and left to check) is a bullet to add to that day's `note('80 Log/<date>', ...)` call in `.tools/build_vault.py`, or a whole call if the day has none (copy the previous day's), then `sync.sh --force`. Today is the machine's local date (Eastern on the Mac).
  - It never blocks and never writes the story or the docs. What it can't see: a deploy piped into another command (`... | tail`) whose failure the pipe hides, and anything done outside Claude Code's Bash tool. The deploys in the day's hand-written bullet (Fly release numbers) remain the check.
  - Where it is installed: twice. `.claude/settings.json` runs it for sessions in the main checkout and any clone. `claude-config/settings.json` (which `install.sh` copies to `~/.claude/settings.json`) runs `$HOME/hate watch/.claude/hooks/remind-vault-log.mjs` for every session on the Mac, because a session in a git worktree (`.claude/worktrees/<name>`) reads its own worktree's copy of the project settings, which is whatever commit the worktree was cut from and may predate the hook, and editing a live worktree's tracked settings would put a change in that session's own diff. A command that fires both copies is handled once (the first to run creates a marker file `hw-log-<tool_use_id>` in the temp folder; the second sees it and stops), and the script ignores any command whose folder path doesn't contain `/hate watch` or `/hate-watch`. The user-settings entry is skipped (`[ -f ... ]`) on a machine without that path. A running session may need a restart to pick up a change to the user settings.
  - Off: `HW_LOG_REMINDER=off`. On a machine without the vault, or when the command is anything else, it prints and records nothing.

## Release flow
- After a change is built and tested, ask before you commit, push or deploy, every time. Don't do any of them unasked. The user wants a say before anything goes public or live, and Apple sign-in is theirs to do.
  - TestFlight builds, over-the-air updates and developer notices have their own rules below.
  - Apple sign-in is part of it: any step that needs an Apple ID login (an interactive EAS build, App Store Connect in a browser) is left to the user.
- Server: deploy from `server/` with `flyctl deploy --remote-only` (or `fly deploy --remote-only`). The app `hate-watch-api` runs on one machine with its SQLite database on a volume at `/data`. Before anything that changes production data, back it up with SQLite's `VACUUM INTO` into `/data`.
  - What the deploy does: `--remote-only` builds the Docker image on Fly's remote builder, so the machine running the command doesn't need Docker (flyctl's help says this is the default anyway). The image comes from `server/Dockerfile`. It starts from `node:24-slim`, runs `npm ci --omit=dev`, copies `src/`, and starts `node --disable-warning=ExperimentalWarning src/index.ts`. Node 24 runs the TypeScript directly (type stripping) and has `node:sqlite` built in, so there is no compile step. `server/.dockerignore` keeps `node_modules`, `data` (the local dev database and recordings), `test`, `*.log`, `fly.toml` and `.gitignore` out of the image. `--ha=false`, in `fly.toml`'s history and the README's first-time setup, is only for the very first deploy, which creates the machine: it keeps it to one. Later deploys keep that one machine, with or without it.
  - What to expect: `fly.toml` sets `strategy = "immediate"`, which replaces the one machine in place, with a few seconds of downtime per deploy. On the old machine, Fly sends SIGTERM. The server logs `[shutdown] SIGTERM`, closes its HTTP server and the SQLite database, and exits (`server/src/index.ts`). The new machine loads the catalog from the database. It only ingests rosters before serving when the catalog is empty, so a normal deploy is serving within seconds. The health check (`GET /health` every 30 s, 5 s timeout, 120 s grace period) has to pass. Afterwards, `curl https://hate-watch-api.fly.dev/health` returns `{"ok":true,"catalog":{...},"live":...}`: the catalog's size and the live engine's status.
  - Why one machine: the live-game poller and every open WebSocket run inside one process. `fly.toml` sets `auto_stop_machines = "off"` and `min_machines_running = 1`, on a `shared-cpu-1x` VM with 512 MB, in region `iad`. Concurrency is counted in connections (each open app holds one WebSocket), with a soft limit of 2,000 and a hard limit of 2,500. The volume `hatewatch_data` is mounted at `/data`, and the database is `/data/hatewatch.db` (`HW_DB`).
  - The backup: `VACUUM INTO` writes a copy of the whole database into a new file. It fails with "output file already exists" if that file is already there, so each backup gets a new name. The image has Node and its built-in `node:sqlite`. One way to run it is to open `fly ssh console -a hate-watch-api` and then run:
    `node -e "new (require('node:sqlite').DatabaseSync)('/data/hatewatch.db').exec(\"VACUUM INTO '/data/hatewatch-backup-2026-10-11.db'\")"`
    (This was checked against a local database with Node 24.21. Against production it is an example, not a step that has been run.) The copy stays on the volume next to the live database.
  - Redundancy (docs/redundancy.md): `server/start.sh` is the image's entrypoint. With the `LITESTREAM_REPLICA_URL` secret set it restores the database from the Tigris replica if the volume has none (and stops the boot if that fails for any reason but "no replica yet"), runs Litestream beside the server, then `exec`s the server. Unset, it only starts the server. `GET /health/deep` is for an outside monitor and deliberately not Fly's check: failing a Fly check would pull the only machine out of routing. Setting or changing a secret restarts the app unless `--stage` is given, so stage it and restart when nothing is live, with the user's OK.
  - What changes production data: a deploy whose code rewrites stored rows on boot is one. For example, b001c54 added `keepFlagsPushed()` in `server/src/fanout.ts`. On its first boot it rewrites every device's `prefs` (NFL flags stay pushed for installs from before), records that it ran (`prefs:nfl-flags-feed`), and never runs again. A command run against the database by hand is another.
- Server switches (`server/src/flags.ts`) turn off what leans on someone else's rights or service without a build: ESPN's video clips, `clips` (all), `clips.highlights`, `clips.feed`, `clips.loss` (and within it `clips.loss.ufc`, a lost UFC fight's clip); and its player photos and team logos, `images` (both), `images.headshots`, `images.logos` (every build then shows a badge in the team's colour with its code instead, `server/src/images.ts`). List or flip one, live within seconds: `fly ssh console -a hate-watch-api -C "node /app/src/flag-cli.ts clips.feed off"` (`on` to undo; it prints the database it opened, which should be `/data/hatewatch.db`). Apps drop a switched-off clip the next time they load the feed (opening the app, reconnecting, pull to refresh). To keep one off for good, `fly secrets set -a hate-watch-api HW_FLAGS_OFF=clips.feed` (restarts the app).
  - What each switch covers (from `FLAGS` in `flags.ts`):
    - `clips`: all of ESPN's video clips.
    - `clips.highlights`: the clips on a game's Highlights tab (its key plays stay).
    - `clips.feed`: the clips on alerts in the feed.
    - `clips.loss`: the winning play's clip, or the game recap, on loss alerts.
    - `clips.loss.ufc`: a lost UFC fight's clip on its loss alerts.
    - `images`: ESPN's player photos and team logos.
    - `images.headshots`: player photos, replaced by a badge in the team's colour with its code and the jersey number.
    - `images.logos`: team logos, replaced by a badge in the team's colour with its code.
  - Every switch is on until it is turned off, and a parent turns off everything under it: `clips` off means every clip, and `clips.loss` off includes `clips.loss.ufc`.
  - Listing them: `fly ssh console -a hate-watch-api -C "node /app/src/flag-cli.ts"` with no arguments. The output starts with a line like `database /data/hatewatch.db (N devices)`, then one line per switch: `on ` or `OFF`, the name, and what it covers. A name that isn't a switch, or a value other than `on` or `off`, prints the usage line and exits with code 1. If the first line names `data/hatewatch.db` instead of `/data/hatewatch.db`, the command opened a local database rather than the volume's.
  - How it takes effect: `flag-cli.ts` writes the setting into the database (the `flags` key). The running server reads it again at most every 5 seconds (`FRESH_MS`), so there is no restart.
  - How the two ways combine: a switch named in the `HW_FLAGS_OFF` secret (comma-separated, for example `HW_FLAGS_OFF=clips.feed,clips.loss`) stays off whatever the database says. `flag-cli.ts ... on` doesn't undo it. The secret also survives a fresh database. Setting a secret restarts the app, which is why the database switch is the quick one.
- Developer notices (a message from Hate Watch in every install's feed, never a push; README "Developer notices"): send one only when the user asks, with its exact title and body (and whether it's urgent) confirmed first, since it goes to everyone. Check the reach with `--dry-run`, then `fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts send --b64 <base64 of {\"title\",\"body\",\"urgent\"}>"` (base64 keeps quotes and apostrophes intact). The same with no command lists them; `withdraw <id>` takes one back. It needs a deploy with notice-cli.ts first.
  - An example of the steps, once the user has confirmed the text: encode the JSON (on the Mac, `printf '%s' '{"title":"Alerts are delayed","body":"ESPN is slow tonight. Alerts may come late.","urgent":false}' | base64`). Run `send --b64 <that> --dry-run`, which prints `would reach N devices (nothing sent)`. Then run the same command without `--dry-run`, which prints `sent <id> to N devices, feed only` and then the notice itself.
  - Where it goes: one event of type `app.notice`, with a feed row for every device that exists at that moment. Devices created later don't get it. The running server passes it to open apps within seconds (`watchNotices`, polling every 5 s). Nothing in Settings turns notices off. `--urgent` (or `"urgent":true`) marks it important, and the app edges it in amber instead of red.
  - Listing and taking back: with no command, `notice-cli.ts` prints each notice as its id, time, how many feeds, `URGENT` if it was, and the title and body. `withdraw <id>` prints `withdrew <id> from N feeds`, or `no notice <id>`. An app that has the notice open keeps it until it next loads its feed.
  - Without `--b64`, `send "Title" "Body"` also works, but the quotes have to survive both the local shell and `fly ssh console -C`, and an apostrophe in the text breaks that. That is why base64 is used.
- App: changes reach people only in a new EAS build. A build goes to both stores, iOS (TestFlight) and Android (Google Play internal testing track). Send one only when asked, from `app/`:
  `npx eas-cli@latest build --platform all --profile production --auto-submit --non-interactive --no-wait`.
  `eas.json` has the App Store Connect app id (no Android block: `eas submit` defaults the Android track to `internal`, and adding one would change the OTA fingerprint), and EAS stores the iOS certificates, profile and API key, the Android keystore and the Play service-account key, so it runs without an Apple or Google login. Android lands on the internal testing track: promote it to production in Play Console (Google reviews it). The optional "TestFlight group setup" step needs one and is skipped, which is harmless. New entitlements would need an interactive build by the user.
  - `eas submit --help` lists that step as `--[no-]auto-testflight-setup`: "Set up an internal TestFlight group for the app (iOS only)".

(These meanings are from `eas build --help`, eas-cli 24.12.1.)

- Before a build: a clean git tree, `npx tsc --noEmit` in `app/`, and the lockfile check below.

- App over the air (EAS Update, `expo-updates`): builds after build 12 take JavaScript and asset changes (screens, wording, styles) without TestFlight. Ask before publishing, as for a deploy. From `app/`, with a clean tree and `npx tsc --noEmit` passing: `npm run update -- --message "…"`. The script sets `EXPO_PUBLIC_API_URL` to production; release builds fall back to production's API anyway, never localhost. Phones download it in the background when the app opens and run it from the next launch (launch never waits: `fallbackToCacheTimeout` 0), so a tester force-quits and reopens up to twice. `runtimeVersion` uses the fingerprint policy: an update reaches only builds with the same native code, so a native change (a new native module, permissions, entitlements, an SDK upgrade) needs a build before its updates. To roll back: `npx eas-cli@latest update:rollback` (interactive: the previous update, or the build's own). Its changes go in `PATCH_NOTES.md` like any app change, noted "(Update)" once published.
  - What `npm run update` runs (`app/package.json`): `EXPO_PUBLIC_API_URL=https://hate-watch-api.fly.dev npx eas-cli@latest update --channel production --environment production`. For example: `npm run update -- --message "Clearer F1 card labels"`. It publishes to the `production` channel, which production builds use. `preview` builds use the `preview` channel and don't get it: to update them, run `EXPO_PUBLIC_API_URL=https://hate-watch-api.fly.dev npx eas-cli@latest update --channel preview --environment preview --message "…"` from `app/` (ask first, as for any update). Don't add it as a `package.json` script: the scripts are part of the fingerprint `runtimeVersion` uses, so a new script stops updates reaching every build already out.
  - Why the API URL is set: `EXPO_PUBLIC_API_URL` is compiled into the JavaScript bundle. Without it, `app/src/lib/api.ts` falls back to `https://hate-watch-api.fly.dev` in a release build, and to `http://localhost:8787` only in a development build (`__DEV__`).
  - What phones do (`app/app.json` `updates`): `checkAutomatically` is `ON_LOAD`, so the app checks when it opens. `fallbackToCacheTimeout` is `0`, so it starts on what it already has. The first open after publishing downloads the update, and the next launch runs it.
  - Why build 12 is the line: `expo-updates` and the fingerprint runtime policy came in with 1601bed, after build 12. Build 12 and earlier have no update client, so they only change with a new TestFlight build.
  - How a rollback works (`eas update:rollback --help`): the update group published before the latest one is published again. If there is none, it rolls back to the update embedded in the build.
  - What counts as native: anything that changes the fingerprint, such as a new native module, a new permission or entitlement, or an Expo SDK upgrade. An update published after such a change matches no installed build until a build with the same native code ships.

Change it there and deploy the server, no build.

    - `players`: what its people are called (`players`, `drivers`, `fighters`).

    - `game` and `events`: one event, and the word on the Scores switch (`game`/`games`, `race`/`races`, `fight`/`fights`).

## Don't run `npx expo lint` in app/
ESLint isn't set up, so `expo lint` installs it and rewrites `package-lock.json`. Local npm 11 accepts that, but EAS Build's `npm ci` (npm 10) rejects it, which failed iOS build 3. EAS uploads uncommitted changes too, so it gets into a build unnoticed. Typecheck with `npx tsc --noEmit` only. Before an EAS build, check the lockfile with `npx -y npm@10.9.8 ci --ignore-scripts --dry-run` on a copy of `package.json` and `package-lock.json`. On a fresh clone, install with `npm ci`, not `npm install`, so the lockfile isn't rewritten.

- Why it happens: `app/package.json` has no ESLint and no lint config, so `npx expo lint` sets them up itself, adding packages to `package.json` and rewriting `package-lock.json`. On EAS, the build installs with `npm ci`, which refuses a lockfile that doesn't match `package.json` exactly as npm 10 reads it.
- Why on a copy: the check runs `npm ci` with npm 10, and running it in `app/` would replace `app/node_modules`. A copy keeps the checkout as it is. For example, from the repo root (the folder name is only an example):
  `d=$(mktemp -d) && cp app/package.json app/package-lock.json "$d" && (cd "$d" && npx -y npm@10.9.8 ci --ignore-scripts --dry-run)`
- What a pass looks like: npm prints `npm warn ERESOLVE overriding peer dependency` warnings (about `react-native-worklets`, a peer of `expo-modules-core`), which are harmless, then a line like `added 617 packages in 1s`. That was the output on October 11, 2026, and it took about two seconds.
- What a failure looks like: `npm error code EUSAGE`, then "`npm ci` can only install packages when your package.json and package-lock.json or npm-shrinkwrap.json are in sync", then one `Missing: <package>@<version> from lock file` line per package. That output was reproduced by adding `eslint` to a copy's `package.json`. If it fails, `package-lock.json` (or `package.json`) has changed from what was committed, and `git diff app/package-lock.json` shows how.
- `npm ci` installs exactly what the lockfile says and never writes it. `npm install` may rewrite it, and with npm 11 that can produce a lockfile npm 10 rejects.

## Patch notes
Keep `PATCH_NOTES.md` up to date with every shipped change, server changes too (written like any other, with no marker), under "Next build". When a TestFlight build is sent, rename that heading to the build number and date and start a new "Next build" above it; `eas build:list --json` gives each build's git commit. Each build's section is pasted as is into TestFlight's "What to Test", so it must be **under 4,000 characters** and **use no emoji**. Update it in the same change as the code, and check each section's length and that it has no emoji (a `\p{Extended_Pictographic}` regex) before committing.

- How the file is laid out: one `##` section per build, newest first. Each section starts with a line on what it covers, such as "Server updates already work on every build." Then come capitalised groups (SCORES, UFC, F1, FOOTBALL, MLB, NBA AND WNBA, EVERYWHERE, FIXES), each a list of one-line changes. A server change works on every installed build as soon as it is deployed, and is written like any other, with no marker (the "(Server)" tags were removed on October 12, 2026). An app change waits for the next build, or for an over-the-air update, marked "(Update)" once published.
- An example of the heading change: when build 12 was sent, "Next build" became "Build 12 (October 9, 2026)" (commit 3941149). A new "Next build (changes since build 12)" started above it.
- Why the limits: TestFlight's "What to Test" field takes at most 4,000 characters, and the section is pasted into it as it is. On October 11, 2026, "Next build" was 3,996 characters and "Build 12" was 3,987, so both were close to the limit.
- One way to check every section, from the repo root:
  `node -e "const t=require('fs').readFileSync('PATCH_NOTES.md','utf8');for(const s of t.split(/^(?=## )/m).slice(1)){const h=s.split('\n')[0],b=s.slice(h.length).trim();console.log(b.length,/\p{Extended_Pictographic}/u.test(b)?'EMOJI':'ok',h)}"`
  It prints each section's length (its text after the heading), `ok` or `EMOJI`, and the heading.

## Two machines (Windows and Mac)
Both machines work from this repo, and neither needs the other turned on. Production runs on Fly and builds run on EAS.
- On a new machine, or after a `git pull`: `bash claude-config/install.sh` sets Claude Code's user settings, this file's notes and the two scouts to the repo's copies. Anything it replaces is kept beside it as `<name>.before-<time>`. Then `npm ci` in `app/` and in `server/`.
  - What it copies: `claude-config/settings.json` to `~/.claude/settings.json`, `claude-config/user-CLAUDE.md` to `~/.claude/CLAUDE.md`, and each file in `claude-config/agents/` (`code-scout.md`, `docs-scout.md`) to `~/.claude/agents/`. A file that differs from the repo's copy is first saved as, for example, `~/.claude/settings.json.before-20261011-153000`. It prints `Claude Code settings in <home>/.claude now match <repo>/claude-config` when it is done.
  - Why the files are LF: Windows git had stored `claude-config/` with CRLF line endings, which breaks a bash script on macOS. `.gitattributes` keeps `claude-config/**` and `*.sh` as LF (b0d26d6).
  - Why `npm ci`: see "Don't run `npx expo lint` in app/" above.
- Logins, once per machine: Claude Code itself, `npx eas-cli@latest login`, `fly auth login`, and GitHub for `git push`. GitHub takes a personal access token (classic, `repo` scope, from github.com/settings/tokens), not the account password: run `git push` in a terminal, give the username `farascioni` and paste the token as the password, and the keychain or credential manager keeps it.
  - What each login is for: the EAS login lets this machine start builds, submits and updates for the `hate-watch` Expo account (`owner` in `app/app.json`). The Fly login lets it deploy and use `fly ssh console` and `fly secrets` on `hate-watch-api`. The GitHub login lets it push to `farascioni/Hate-Watch-2.0`.
- Not in git, so each machine keeps its own: `.claude/settings.local.json`, `app/.expo/`, `server/data/` (the dev database, which the server rebuilds from ESPN on first start), and Claude's memory under `~/.claude/projects/`. This file is the shared copy of the notes that matter.
  - The dev database is `server/data/hatewatch.db`. On first start with an empty catalog, the server ingests every league's teams and rosters from ESPN before it starts serving (`server/src/index.ts`).
- Game recorders (the Mac only): the scripts in `server/data/recordings/` (`record-nba.ts`, `record-mlb.ts`, `record-nfl.ts` and the others) record a live game from ESPN so the alerts can be checked against it afterwards. `server/data` is not in git, so `recorders.py` and its registry `recorders.jsonl` there are not either.
  - Why a registry: a background task a session starts dies when the Claude app restarts. On October 11, 2026 a restart at 3:03 pm ET stopped three NBA recorders, a production log stream and a deploy watcher with no sign, and only the recorder started detached survived. So every recorder is launched through `recorders.py` (detached, in its own session, under `caffeinate -is`, its parent launchd), and its command and window are one line in `recorders.jsonl`: `name`, `owner` (the session that reads the recording), `cwd`, `argv`, `out` (the `.jsonl` it writes, which is also how a running one is found), `startAt` (the launch sleeps until then; omit it for a script that waits by itself), `stopAt`, and `follows` for a companion that writes no start or stop line. The header of `recorders.py` documents the fields.
  - `recorders.py` prints the state of each entry (running, waiting, done, dead) and any recording that looks dead and is not registered. `--restart` also relaunches every dead entry. A recorder that already wrote more than its start line continues in `<name>-partN.jsonl`, because the scripts keep what they have seen in memory and would log every play again as new; a replay has to read the parts together. A second run starts nothing twice: it finds a running recorder by its output path, and a lock folder keeps two checks apart.
  - A service entry (the dev server on port 8787) counts as running while its port listens, is never split into parts, and has no `stopAt`. A service with no port (the call-count collector `calls-test/collect.py`) gives `match`, a piece of its command line, and counts as running while a process other than a shell, grep or ps has that in its command.
  - It runs on its own, two ways. `.claude/settings.json` has a SessionStart hook that runs `recorders.py --restart` and puts the output in the session's context. The hook does nothing on a machine without the script. It is in the tracked settings, not `.claude/settings.local.json`, because a session in a git worktree (where side sessions run) does not read the main checkout's local file.
  - And a LaunchAgent, `com.hatewatch.recorders` (`~/Library/LaunchAgents/com.hatewatch.recorders.plist`, a copy beside `recorders.py`), runs `recorders.py --agent` at login and every 5 minutes, so recorders come back after a reboot with no Claude session open (the hook alone waits for one). `--agent` is `--restart` that prints nothing when nothing needed relaunching (otherwise the state of every entry, in `agent.log` beside the script) and gives up on an entry after 6 relaunches of its own (a crash loop; the count starts over once an entry has stayed up for 30 minutes). It marks each entry it relaunches `"toTell": true`; every session's run of `recorders.py` (the hook) then prints "the background agent relaunched it ... tell <owner>" until `recorders.py --told <name>` (or `all`) clears the mark, so the owner session hears about a relaunch nobody was present for. The Mac must be awake and logged in; install on a new Mac with `cp com.hatewatch.recorders.plist ~/Library/LaunchAgents/` and `launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.hatewatch.recorders.plist`, remove with `launchctl bootout gui/$(id -u)/com.hatewatch.recorders`.
  - Naming a recording session: one session per game, started by the "Game recorders for tonight" session (so it nests under it in the sidebar). Title `<AWAY> at <HOME> <LEAGUE> recording` with ESPN's abbreviations (`CLE at TB MLB recording`, `COL at DAL NHL recording`), short name `rec-<league>-<away>-<home>` in lowercase (`rec-mlb-cle-tb`, `rec-nhl-col-dal`). The registry entry's `owner` names that session, so a relaunch notice reaches it. A session that took over a recorder later (a post-game report) is retitled to this form while it owns the recorder.
  - Production log streams (`fly logs`) and deploy watchers are not in the registry. A session that records a game may read production (the user allowed it on October 12, 2026: `fly logs`, read-only queries, `/health`, `fly status`, `fly releases`), so a log stream or deploy watcher belongs to the session that started it. Anything that changes production (a deploy, a restart, a database write, a server switch, a developer notice, a secret) still needs the user's OK for that action, and a deploy or restart also waits for nothing live and a `VACUUM INTO` backup.
