## Lock screen scoreboard

**In short:** with the switch on in Settings, an iOS Live Activity on the lock screen lists the live games of the teams the device tracks: a favorite's games first, then most hated, then the rest, four lines and "+N more" (four layouts to pick in Settings: Compact; Detailed, three two-line games; Grid, four cells two across; Hero, the top game big and two lines). The server builds each device's board and pushes it to Apple itself (`server/src/live-activity.ts`, `apns.ts`; inert until the APNs key and the `liveActivity` switch are set); the app starts it and sends its push token and its most hated list, so that list now leaves the device while the board is on. Needs a native build once (the widget extension); after it, the board's wording, colors and rows change with a server deploy, and the widget's layout code (`ScoreboardActivity.tsx`) ships over the air with an EAS Update, using only the components and modifiers that build already has.

## What it shows

- **Games:** a game is on a device's board while it is live, and for 10 minutes after it ends (shown as "Final"). Games not started are not shown. F1 and the UFC are not on it (`GAME_LEAGUES` leaves them out).
- **Order** (`buildBoard` in `server/src/live-activity.ts`): the games of a favorite team first (heart), then a most hated team's, or the team of a most hated player's (star), then the games of teams the device only tracks. Inside each, live before final, then the earlier start. Only a favorite's game appears without the team being tracked; a most hated team that is not tracked is left off.
- **A row:** `♥ AWAY 3  ❌ HOME 2` and the status on the right (`statusLine` in `live-activity.ts`: ESPN's inning, quarter or clock, then baseball's outs and count, or football's down and distance, in red while live; "Final" in grey; hockey and basketball give the clock only, since the card has no power play or run). Each team has its own color and mark (`ac`/`hc` the away and home color, `am`/`hm` the mark before its code): a favorite is gold with a heart, a most hated team (or the team of a most hated player) red with a red X (❌), every other team white; both sides can be marked in one game, and a team that is both is red with the X, as on every card and feed row. Compact, Detailed, Grid and Hero all draw it (the hero's code and score either side take their team's color); the status on the right stays red while live. Four rows at most (the lock screen has room for about that many); the rest are counted in "+N more". In the Dynamic Island, the first game's teams and score.
- **Dynamic Island and CarPlay/watch:** compact and minimal show the first game; expanded shows the first game across the middle and the rest below; the small banner (CarPlay, watch) shows the top two. All regions are defined in the first build because adding one later needs a build (their contents change over the air).
- **Tapping** it opens the app.
- **Four layouts** (Settings, "Scoreboard layout", shown while the board is on: a Compact / Detailed / Grid / Hero choice; stored on the device as `hw.liveLayout` and sent as `layout` on every `PUT /me/live-activity`, kept in `live_activities.layout`; the props carry it as `lay` 0 to 3 and `MAX_GAMES = [4, 3, 4, 3]` is how many games each fits, an estimate not yet checked on a device). **Compact** (`lay: 0`) is the one above. **Detailed** (`lay: 1`) gives every row a second line: `sub` in `sc` (baseball `1-2 · 2 outs · P: Name`; football `KC ball · 3rd & 6`, plus "Red zone"; hockey `Shots 24-19`; otherwise the last play, clipped), `bs` the bases as "101" (first, second, third; baseball only), and `wp`/`wl`, the win chance (0-100) of the side the device tracks, labelled "KC 72%" (drawn as a bar). The detailed Dynamic Island, long-pressed, gives the top game its scores either side, its clock and bases in the middle, its sub line and win bar under them, then the others as one-line rows. **Grid** (`lay: 2`) draws the games as cells two across, each the away and home code and score on two lines with one short status under them: a live row's `r` leaves out baseball's count (`statusLine(g, false)`: "Bot 8th · 1 out", "Q4 2:14 · 3rd & 6"), since a half-width cell has no room for it. **Hero** (`lay: 3`) draws the first game big: each team's code and score either side, and in the middle its clock (`r` is the plain status) with the bases (`bs`) and `sub`, which holds the count and outs, the down and distance or the shots (`heroLine`); the other games are compact rows, and a favorite is always the first. Only the banner differs between layouts: the compact and minimal Island regions, the Island's expanded regions and the CarPlay/watch banner are the compact ones in every layout but Detailed (Hero's expanded Island uses the first game's plain status, so it leaves out the outs and count that Compact shows). Baseball's second line (Detailed) and the hero's middle change on every pitch, so expect a priority-5 push about every 30 seconds per device during an at-bat; Compact and Grid change less often.
- **Older builds:** the widget code comes from the app's JS, so a build gets a new layout the next time it takes an EAS Update (same runtime fingerprint as the update). Until then it draws what it has: a build without the per-team colors draws a row in one color, the tier's; a build without Detailed, Grid and Hero draws every row as Compact (it ignores the extra fields; the server still sends three rows for Detailed and Hero), so the choice changes little there. The team colors reached Build 19 as an update on October 17, 2026. The app does not hide the choice on such a build (no build-number check without a new native dependency).

## How it works

- **App** (`app/src/lib/liveScoreboard.ts`, `app/src/widgets/ScoreboardActivity.tsx`): `expo-widgets` draws the activity from props in the widget extension's own runtime (no hooks, no imports of ours). When the app opens or comes back to the foreground, and when the most hated list changes, it sends the list and asks the server for the board now (`PUT /me/live-activity`), then starts the activity (or updates the one already up, ending any extra), and sends the activity's push token (`getPushToken`, `addPushTokenListener`). No board means no live game: it ends the activity. Switching it off in Settings, and "Delete all my data", end it and call `DELETE /me/live-activity`.
- **Server** (`server/src/live-activity.ts`, `apns.ts`): every game change (`onGameChange` in `scores.ts`, debounced one second) and a 30 second sweep (a final leaving the board) rebuild each device's board and send it if it differs from the last one sent. A change of score or of a game going final goes at APNs priority 10, a clock or inning change at 5 and at most every 30 seconds per device (ESPN's status text carries the clock, so it changes every few seconds; the sweep catches up). No board sends an `end`. Apple's 410, or 400 BadDeviceToken, clears the stored token. Nothing is sent unless `APNS_*` and the `liveActivity` switch (`server/src/flags.ts`) are set.
- **Props and what updates without a build:** the widget function is serialized to a string by the `'widget'` babel plugin when Metro bundles the JS, so it is part of the OTA bundle; the app stores it in the App Group at launch (`createLiveActivity`) and the extension's JavaScriptCore evaluates it on each render. So the layout (rows, spacing, colors, which fields it reads) changes with `npm run update`, reaching phones the way any update does (downloaded on open, run from the next launch, up to two relaunches). The limit is the native side: the components and modifiers on the widget's `globalThis` (`@expo/ui/swift-ui` and its modifiers) are those of the installed build's `ExpoWidgets.bundle`, so a new component or modifier, a new Dynamic Island region, a bundled image or an entitlement needs a build. A layout that throws shows a red box with the error instead of the board. The widget draws what the server sends. Each row carries its line already written and colored (`l` left text, `r` right text, `lc`, `rc` their colors) and the board `mt` (the "+N more" line, empty for none), with the raw fields (`a`, `as`, `h`, `hs`, `st`, `live`, `t`) beside them and `v: 1` the props' version. Wording, marks, colors and the row count (`MAX_GAMES`) change with a server deploy. The widget uses `l`/`r`/`lc`/`rc`/`mt` when present and its own formatting when not; `ac`/`hc`/`am`/`hm` (builds after 19) draw each team in its own color, and a build without them draws the whole line `l` in `lc`, which is the tier's color (gold a favorite's game, red a most hated one's, white the rest). Rule: props only gain fields, never change or lose one, since a build already out draws only the fields it knows (the widget code on a phone lags the server until its update lands). A new region or a bundled image needs a build.
- **Routes:** `GET /me/live-activity` → `{board}`; `PUT /me/live-activity` with any of `mostHated` (keys), `layout`, `activityToken`, `sandbox` → `{board}`; `DELETE /me/live-activity`. A `null` board also means the switch is off.
- **Table:** `live_activities` (`device_id`, `activity_token`, `sandbox` for a development build's token, `most_hated` as JSON, `layout` 0 compact, 1 detailed, 2 grid, 3 hero, `updated_at`), removed with the device.
- **Alerts:** none. The board is not an alert and does not touch `publish()` or the duplicate protection.

## Privacy

Most hated lived only on the device (`docs/deploy.md`, Most hated). With the board on, the app sends those keys (teams and players, at most 200) to the server so it can sort. They are stored in `live_activities`, used for nothing else, and removed by switching the board off, by a Plus lapse (the list is emptied and the new empty list is sent), and by "Delete all my data". With the board off, nothing is sent.

## Setting it up

1. In the Apple Developer account, Keys, make a key with Apple Push Notifications service (APNs) enabled and download the `.p8` once. It is not the App Store Connect API key.
2. `fly secrets set --stage -a hate-watch-api APNS_KEY_P8="$(cat AuthKey_XXXX.p8)" APNS_KEY_ID=<key id> APNS_TEAM_ID=<team id>` (a literal `\n` in place of newlines also works), then restart when no game is live (a secret change restarts the app).
3. `fly ssh console -a hate-watch-api -C "node /app/src/flag-cli.ts liveActivity on"` turns it on or off, live. List the switches the same way.
4. The app needs a new native build (the widget extension and the Live Activities entitlements: `expo-widgets` with `enablePushNotifications`, `NSSupportsLiveActivities` and `NSSupportsLiveActivitiesFrequentUpdates` in `app.json`). The first build needs the user's interactive Apple sign-in to register the extension target. Over-the-air updates cannot add it.
5. Development builds use Apple's sandbox host (`sandbox: true` is sent from `__DEV__`); TestFlight and App Store builds use the production host.

## Limits

- **The app starts the board, not the server.** If the system ends it (after about eight hours, or the user swipes it away) it comes back the next time the app opens. Push-to-start (iOS 17.2) is not built.
- **Not tried on a device.** The lock screen's height limit, Apple's update budget (frequent updates are requested, and the user can switch them off) and the activity's push token reaching the server need a real build to check.
- **Only games:** F1 and the UFC are not on the board.
- **Plus is checked on the device**, so a favorite or most hated exists only for a subscriber; the board itself is not a Plus perk.
