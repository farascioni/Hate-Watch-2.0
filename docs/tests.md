## Tests

**In short:** `npm test` in `server/` runs every `test/*.test.ts` file with Node's own test runner: 613 tests in 78 files, offline, in about 4 seconds, all passing on October 19, 2026. Next to them are scripts that read live ESPN (replays of finished games, the two-feed check, an F1 replay, a catalog audit) and an end-to-end smoke test against a running server. On the Mac, recordings of live games under `server/data/recordings/` (not in git) are replayed through the real game tracker and checked against what production sent.

```bash
cd server
npm ci                        # once, on a fresh clone (not npm install: it can rewrite the lockfile)
npm test                      # every test/*.test.ts: 613 tests, offline, ~4s
node --test test/notices.test.ts   # one file
npm run typecheck             # tsc --noEmit
node test/replay.ts           # replays real finished games; asserts tracked score == final score
node test/core-vs-site.ts     # both ESPN sources produce identical detections
HW_DEV=1 npm start & node test/smoke.ts   # end-to-end: search, follow, ws delivery, prefs, mute, unfollow, auth
node test/f1-replay.ts        # F1 alert logic on the real, current race weekend vs ESPN's classification
node test/verify-catalog.ts   # audits the ingested catalog: duplicates, images, logo fallbacks
node test/find-nobletiger.ts  # finds real NOBLETIGERs in recent MLB games
```

**How the unit tests run.** `npm test` is `node --disable-warning=ExperimentalWarning --test test/*.test.ts`. Node 22.18 or later (`engines` in `package.json`) runs the TypeScript files as they are, with no build step. Every test file sets `process.env.HW_DB = ':memory:'` before it imports server code (`db.ts` opens its file on import), so the tests never touch `server/data/hatewatch.db`; `share.test.ts` also builds a throwaway database in the system's temp folder to test the share-code migration, and deletes it. ESPN is faked through seams the live code reads from (`liveDeps.getJson` in `live.ts`, `f1Deps` in `f1.ts`), and the play shapes and wording are ESPN's own from real games, named in each file's header comment. Three fixtures are checked in, each the plays of games trimmed from their live recordings: `test/fixtures/alds-game5-401907994.json` (ALDS Game 5) and `test/fixtures/nlcs-game1-401908030.json` (NLCS Game 1: the Dodgers' last half-inning, Turang's tying homer, the two other scoring plays, the roster and the series as the scoreboard and the summary had it). The third, `test/fixtures/mlb-oct12-review.json`, holds eleven scenarios from NLCS Game 2 and ALCS Game 1 (the half-innings the reports found problems in, each read as ESPN had it; the first-hour scenarios of NLCS Game 2 are partly synthetic, as the scenario says).

**Scripts that read live ESPN.** These aren't run by `npm test`, and they need the network:

- `test/replay.ts [league:eventId …]`: replays finished games through the detectors as the live tracker would (default: `mlb:401907973`, `nfl:401872963`, `nhl:401891781`, `nba:401811026`). For each it prints PASS or FAIL for lead changes merged into one alert and for the tracked score against ESPN's final, the alerts by type, and how many same-id detections collapsed into one, as `publish()` would. Exit status 1 on any FAIL. This is the canary for ESPN changing its fields.
- `test/core-vs-site.ts`: the three games above (not the NFL) through core plays, site plays and the merge; PASS only if all three give the same alerts in the same order.
- `test/smoke.ts`: against a running server (`HW_URL`, default `http://localhost:8787`) started with `HW_DEV=1` (it uses `POST /dev/simulate`). It registers a device, searches, follows Bryce Harper and the Eagles, and checks WebSocket delivery (it prints the measured milliseconds), a type switched off, a per-player choice beating the global one, a muted target still reaching the feed, unfollowing, a bad token getting 401, `/privacy` and `/support`, and "Delete all my data" closing the socket (4401) and voiding the token. On a fresh database the server ingests rosters for about 30 seconds before it serves, so start it, wait for `[boot] catalog` in its output, then run the script.
- `test/f1-replay.ts [eventId]`: the F1 results logic on a real weekend (the current or latest by default), against ESPN's classification.
- `test/verify-catalog.ts`: audits the ingested catalog: unique players and teams, an image for every row, image sizes, and every logo fallback a real 404 from ESPN.
- `test/find-nobletiger.ts [maxGames=40] [YYYYMMDD]`: runs the detector over recent finished MLB games until it finds NOBLETIGERs, and prints near-misses too.

**Recordings and replays** (`server/data/recordings/`). `server/data/` is in `.gitignore`, so this folder exists only on the Mac that made it; nothing in it reaches GitHub or the other machine. It holds recordings of live games read from ESPN exactly as the server reads them (cache-busted, the same URLs; MLB, NBA and EPL games every 5 seconds, college football every 15, F1 and UFC every 10), the scripts that make and replay them, and the scripts that check a replay:

- **Recorders** (`record-mlb.ts`, `record-mlb-sb.ts`, `record-nba.ts`, `record-epl.ts`, `record-cfb.ts`, `record-f1.ts`, `record-ufc.ts`, `record-ufc-fc.ts`). Each writes a `.jsonl` with a line per change: every play the first time it's seen and again whole each time ESPN edits it (`core`/`core-edit`, `site`/`site-edit`), plays that vanish (`core-gone`), and the header on change; the NBA and EPL recorders also log reads slower than the tracker's 4s timeout (`slow`). `record-cfb.ts` wrote each play once until October 14, 2026; it now writes a play again with `revision: true` when ESPN changes it and `play_gone` when ESPN drops it (Delaware at Middle Tennessee had 32 of 175 plays edited and 3 replaced), and `replay-del-mtsu-edits.ts` follows them (for a recording made before that, it shows each play as first recorded and then final after 45 seconds, `EDIT_AFTER_MS`; `replay-del-mtsu.ts` is `replay-cfb-noon.ts` on that game's two files). Full summaries go to `<out>-summaries.jsonl.gz`, the final summary and core plays to `<out>-final-summary.json` and `-final-core.json`, and the NBA and EPL recorders also save the standings before the game and 2, 15 and 30 minutes after it (`standings-after.ts` does it for MLB).
- **The registry** (`recorders.py`, `recorders.jsonl`): one line per recorder that should be running, and `recorders.py --restart` relaunches any that died (the Claude app restarting stops what a session started in the background; so does a crash or a reboot). A LaunchAgent runs `recorders.py --agent` at login and every 5 minutes, so they return after a reboot with no session open (`docs/working-in-this-repo.md`, "Game recorders").
- **Replays** through the real `GameTracker` with virtual timers: `replay-mlb.ts` (ALDS Game 5, 401907994; `SRC=<server/src> FINAL=sb|fallback UNTIL=<iso> node replay-mlb.ts <out.json>`, many devices tracking single targets and combinations), `replay-cfb-noon.ts` (the twelve noon college games of October 10, 2026, three devices a game), and `replay-epl.ts` (Manchester City at Liverpool, 401879264, October 11, 2026).
- **The checks** on a replay: `check-mlb.py <out.json>` (an independent tally, by regex over the final plays, of what should have alerted), `vs-prod.py <out.json>` (the replay's alerts against production's `[event]` log lines for the game), `edits-mlb.py` (ESPN's edits to the game's plays after posting them, and the recorder's gaps between reads), and `prod-read.js` (read-only: what production sent for the game, how many feeds and pushes, no device ids or tokens).
- **The post game recording report** (every recording, any sport): when a recorded game ends, its session replays the recording through the real tracker, compares the replay with what production sent (a session that records a game may read production without asking: `fly logs`, read-only queries, `/health`, `fly status` and `fly releases`, which the user allowed on October 12, 2026; anything that changes production still needs their OK) and with an independent count of the plays, and publishes the result as a private claude.ai Artifact called a post game recording report. It is one page for every sport: the score table (a line score by period, a results table for F1 or UFC, or none), the facts, then one card per finding with its severity, the alerts as they went out drawn as phone banners (Eastern time, who got each, pushed or feed only), what is wrong, the proposed change and the alert's text before and after, and then "What looked right" and "How this was checked". The user marks each finding Approve, Change or Skip, with a note. The choices are saved in the page's own database (collection `decisions`, one document per finding id: F1, F2 and so on), and only approved findings are built, in a worktree, with tests made from the game's plays. These reports are the bug list that recordings produce, so they are how bugs are found and tracked across leagues. The first was the ALDS Game 5 report (13 findings, all approved and shipped as 214e7c0). The page template, a builder that checks a report's data, a blank data file and the ALDS data as a worked example are in `docs/post-game-recording-report/`, with the steps and every data field in [post-game-recording-report.md](post-game-recording-report.md).

A change to alerts is checked by replaying the recorded game it's about and comparing the alert count before and after ([docs/duplicate-alerts.md](duplicate-alerts.md), "How to change alerts safely").
