# Hate Watch 😈

**In short:** Hate Watch is a phone app for following the athletes and teams you can't stand, and getting a push the moment something bad happens to them. It is two programs in one repository: an Expo app in `app/` and a Node server in `server/` that reads ESPN, spots bad plays in live games and sends them to the people who track them. Production is one Fly.io machine (`hate-watch-api`) with a SQLite database, and app builds come from EAS.

The rest of this README is the reference for how everything works. **Run it** starts the app and the server on your own machine. **Deploy** covers the server on Fly.io, the iOS and Android builds on EAS, App Store Connect, donations and the icons. **Data** explains where teams, players and images come from and how the catalog stays free of duplicates and wrong faces. **Real-time** covers how fast an alert arrives and how football plays that ESPN rewrites are handled. **Notifications** lists every alert type, the defaults for new installs and every setting. Then the app's screens and features: the **Scores tab**, the **Stats pages**, the **Successful Hate Watch counter**, the **Leaderboard**, the **Startup guide**, **An alert on its own screen**, **Developer notices** and **Sharing an alert**. **Tests** says how the code is checked, and **Known limits** what isn't covered or can't be. The UFC and college football are described in `PATCH_NOTES.md` and in the header comments of `server/src/ufc.ts` and `server/src/cfb-poll.ts`. Releasing is in `CLAUDE.md`, and the Google Play release in `docs/android-release.md`.

Track the athletes and teams you can't stand. Get a push the moment something bad happens to them.

- **`app/`**: the iOS and Android app, built with Expo SDK 57 (`expo` ~57.0.26), React Native 0.86 and Expo Router. It also runs on the web, for development. It talks to the server over REST and a WebSocket. The server's address is `EXPO_PUBLIC_API_URL`, or `http://localhost:8787` in a development build and `https://hate-watch-api.fly.dev` in a release build (`app/src/lib/api.ts`, `API_URL`). The WebSocket is the same address with `ws` in place of `http`, at `/ws` (`WS_URL`).
- **`server/`**: the Node backend. Node runs its TypeScript sources directly (`"engines": { "node": ">=22.18" }`, and Node 24 in the Docker image), with SQLite from `node:sqlite`. It has three jobs:
  - It builds a catalog of every team and player from ESPN (`server/src/catalog.ts`, see Data below).
  - It watches live games and detects bad plays (`live.ts`, `detectors.ts`).
  - It sends each alert to the feed, to the open apps over the WebSocket, and to phones as a push through Expo Push, which hands it to APNs (iOS) or FCM (Android) (`fanout.ts`, `push.ts`).
- **Nine leagues**, in the order the app lists them (`LEAGUE_IDS` in `server/src/leagues.ts`): the NBA, MLB, NFL, NHL, Formula 1, the Premier League (EPL), the UFC, college football (FBS teams only, no players) and the WNBA. The WNBA always goes last, wherever a league is added in `LEAGUES`. Each league's look in the app (its chip colour, its filter, what its people and events are called) is set by `ui` in `LEAGUES`, so it changes with a server deploy rather than an app build.

```
ESPN (core plays + site summary, polled in parallel every 2s per live game; college football: summary drives, every 5s)
   │
   ▼
GameTracker ─► league detectors ─► publish() ─┬─► events table (deduped by deterministic id)
scoreboard (10s) / standings (60s) /           ├─► per-follower prefs filter (type, league); push also skips muted + quiet hours
injuries (30s)                                 ├─► feed rows ─► WebSocket frame to open apps (≈ms)
college football: scoreboard (20s, 5 min       └─► Expo Push ─► APNs / FCM (app closed)
  when no game is near) / standings (10 min),
  no injuries or news
```

How to read the diagram, checked against `server/src/live.ts` and `fanout.ts`:

- **Each live game is read every 2 seconds** (`HW_LIVE_POLL_MS`, default 2000). Each read fetches ESPN's core play-by-play and the site summary at the same time (`Promise.allSettled`) and merges their plays (`mergePlays`). Soccer and college football read the summary alone. A college football game is read every 5 seconds (`HW_TEAMS_ONLY_POLL_MS`).
- **Slower loops:** the scoreboard every 10 seconds (`HW_SCOREBOARD_MS`), to find games going live or final. Standings every 60 seconds (`HW_STANDINGS_MS`). Injury reports every 30 seconds (`HW_INJURIES_MS`).
- **`publish()` stores each alert once** in the `events` table. Its primary key is a deterministic id built from what happened (for example game, play, type and athlete), so reading the same play again never alerts twice.
- **Each follower's settings decide what they get.** An alert type or league they switched off is skipped, unless they set that target's alerts on their own (a per-target setting beats the global switches, `typeEnabledFor`). Push also skips a target they muted (it still reaches their feed) and their quiet hours (default off, 23:00 to 08:00 America/New_York, `DEFAULT_PREFS` in `fanout.ts`).
- **Open apps** get the alert as a WebSocket frame within milliseconds. **A closed app** gets it as a push.

## Run it

**In short:** Start the server with `cd server && npm ci && npm start`. It listens on port 8787 and keeps its development database in `server/data/hatewatch.db`. On the very first start, that database is empty, so the server reads every league from ESPN before it starts listening. Start the app with `cd app && npm ci && npx expo start`. A development build talks to `http://localhost:8787` unless `EXPO_PUBLIC_API_URL` says otherwise. Push needs a physical phone and a development build. `HW_DEV=1` adds a route for sending yourself a test alert.

```bash
cd server && npm ci && npm start          # first start: reads every league from ESPN, then serves :8787
cd app && npm ci && npx expo start        # press i / a, or w for web
```

Install with `npm ci`, not `npm install`. `npm ci` installs exactly what `package-lock.json` says and never rewrites it. A rewritten lockfile has broken an EAS build before (see CLAUDE.md). Don't run `npx expo lint` in `app/` either: ESLint isn't set up, so it installs ESLint and rewrites the lockfile.

**The server, step by step** (`server/src/index.ts`, `db.ts`):

1. `npm start` runs `node --disable-warning=ExperimentalWarning src/index.ts`. Node runs the TypeScript directly, with no build step. That needs Node 22.18 or later (`engines` in `server/package.json`).
2. `db.ts` opens the SQLite database at `HW_DB`, which defaults to `data/hatewatch.db`. The path is relative to the folder you start in, so start the server from `server/`. The folder is created if it's missing (`mkdirSync`). The database runs in WAL mode, with foreign keys on, and its tables are created if they don't exist: `teams`, `players`, `devices`, `follows`, `events`, `feed`, `hate_watches` and `kv`. Columns added after launch are added to an older database on start: `events.share_code`, `players.positions`, `events.clip` and `feed.extra`. `server/data/` is in `server/.gitignore`, so each machine has its own development database.
3. `loadCatalog()` reads the teams and players into memory.
   - **If the catalog is empty** (a new machine, or a deleted database), the server logs `[boot] catalog empty; ingesting rosters from ESPN…` and reads every league before it listens. Fly's health check gives a first boot 120 seconds (`grace_period` in `server/fly.toml`), whose comment estimates 30 to 60 seconds. The latest full read of the development database, on 2026-10-11, came to 309 teams and 6,980 players.
   - **If a league is missing** from a catalog that isn't empty (a deploy that adds a league, as F1, the WNBA, the UFC and college football each were), the server logs `[boot] catalog missing …; ingesting in the background` and serves at once. The read it then starts covers every league, not just the missing one.
4. It logs `[boot] catalog { teams, players }` and `[boot] next roster refresh in N min`, then schedules the 6-hour refresh (see Data).
5. It starts the API on `PORT` (default 8787; production uses 8080, set in `fly.toml`), the live-game engine (`engine.start()`), and the watcher that sends developer notices to open apps (`watchNotices()`).
6. On `SIGTERM` or `SIGINT` (Ctrl-C, or a deploy), it closes the HTTP server and the database and exits.

To check it's up, run `curl localhost:8787/health`. It answers `{ ok: true, catalog: { teams, players }, live: … }`. `GET /catalog/report` returns the last ingest's report, with each league's counts and every problem it noted.

**Dev mode: a test alert.** Starting the server with `HW_DEV=1 npm start` adds `POST /dev/simulate` (`server/src/api.ts`). The route needs a device's token, like the app's own requests. It takes an optional `targetKey` and `type` in the body. Without them, it picks one of the device's follows at random, and an alert type at random that fits it (a player or team alert for that league). It then publishes the alert through the normal path, so it reaches the feed, the WebSocket and push. The alert's title reads `[TEST] <name>: <alert label>`, its body "Simulated event from /dev/simulate", and its id is `sim:<uuid>`. A device that follows nothing gets 400 "follow something first". In the app, Settings shows a "Send a test event (dev)" button in every development build (`__DEV__`). That button calls this route, so against a server started without `HW_DEV=1` it fails with "Simulate failed" (404, "no route").

## Deploy

**In short:** Hate Watch reaches people in three ways. Each has its own command, and none of them needs the other machine. **The server** (`server/`) runs on Fly.io as the app `hate-watch-api`: one machine, with SQLite on a volume. A server deploy reaches every installed build within seconds. **The app** (`app/`) is built in the cloud by EAS (Expo Application Services) and sent to TestFlight and the App Store, and later Google Play. **Over-the-air updates** (EAS Update) send JavaScript and asset changes to builds after build 12 without a new build. The day-to-day release rules (ask first, the exact commands, backups, server switches, developer notices, patch notes) are in `CLAUDE.md` under "Release flow". This section covers first-time setup and how each piece is configured.

**Google Play (Android):** step-by-step guide in [docs/android-release.md](docs/android-release.md), written for releasing without owning an Android phone.

**Which one a change needs:**

| The change | How it goes out | Who gets it |
|---|---|---|
| Anything in `server/` (alerts, wording the server writes, how each league is shown) | `fly deploy --remote-only` from `server/` | Every install, every build, within seconds |
| Turning off ESPN's clips or images | A server switch (`server/src/flag-cli.ts`), no deploy | Every install, within seconds; a clip already in a feed goes at its next feed load |
| A message to everyone | A developer notice (`server/src/notice-cli.ts`) | Every install's feed, never pushed |
| JavaScript or assets in `app/` (screens, wording, styles) | `npm run update` from `app/` | Builds after build 12 with the same native code, from their next launch |
| Native code (a new native module, permissions, entitlements, an SDK upgrade) | A new EAS build, then TestFlight or the stores | Whoever installs the new build |

### Server → Fly.io

**In short:** the server is one Docker image (`server/Dockerfile`, Node 24 running the TypeScript directly) on one always-on Fly.io machine named `hate-watch-api` in `iad` (US East). Its SQLite database is at `/data/hatewatch.db`, on a 1 GB volume. Setting it up the first time takes six commands: log in, create the app, create the volume, an optional secret, the first deploy, and a health check. After that, a deploy is `fly deploy --remote-only` from `server/` (`CLAUDE.md`, "Release flow"). A deploy replaces the machine in place, with a few seconds of downtime, and the server shuts down cleanly on SIGTERM. It costs a few US dollars a month.

**What you need:** a [Fly.io](https://fly.io) account with a card on file, and `flyctl` installed (`pwsh -Command "iwr https://fly.io/install.ps1 -useb | iex"` on Windows). Docker isn't needed locally, because Fly builds the image on a remote builder.

**First-time setup**, from `server/`:

```bash
fly auth login
fly launch --copy-config --no-deploy        # creates the app from fly.toml; rename it if "hate-watch-api" is taken
fly volumes create hatewatch_data --region iad --size 1 --count 1
fly secrets set EXPO_ACCESS_TOKEN=...       # optional: only if Expo push security is enabled
fly deploy --ha=false
curl https://hate-watch-api.fly.dev/health  # → {"ok":true,"catalog":{"teams":124,"players":5033},...}
```

What each step does:

1. `fly auth login` signs this machine in to Fly. It's needed once per machine.
2. `fly launch --copy-config --no-deploy` creates the app on Fly from `fly.toml` as it is, without prompting for its settings (`--copy-config`) and without deploying yet (`--no-deploy`). App names are global on Fly. If `hate-watch-api` is taken, change `app` in `fly.toml`, and also the URL in `app/eas.json` (see "If you rename the Fly app" below).
3. `fly volumes create hatewatch_data --region iad --size 1 --count 1` creates one 1 GB volume in `iad`. Its name has to match `source` under `[[mounts]]` in `fly.toml`, which mounts it at `/data`.
4. `fly secrets set EXPO_ACCESS_TOKEN=...` is only needed if enhanced push security is turned on in Expo. `server/src/push.ts` then sends it as a bearer token with every push request. Without it, pushes go out with no token.
5. `fly deploy --ha=false` builds and starts the server. flyctl creates spare machines by default (`--ha`, default true). `--ha=false` keeps it to exactly one, which this server needs (below).
6. `curl https://hate-watch-api.fly.dev/health` checks that it's up. `/health` returns `ok`, the catalog's size (`{"teams":…,"players":…}`) and `live`: the games, F1 sessions and UFC cards being tracked right now. The counts in the comment above are from the first setup. The catalog has grown since (see "Data" below).

**The first boot:** with an empty database, the server ingests every league's teams and rosters from ESPN before it starts listening (`server/src/index.ts`, `[boot] catalog empty; ingesting rosters from ESPN…`). `fly.toml` gives the health check a 120 s grace period for that. After that, rosters refresh in the background every 6 hours. A deploy with an existing database serves at once, and a newly added league is ingested in the background.

**Deploying after that** (`CLAUDE.md`, "Release flow", where asking first and backing up first are also covered):

```bash
cd server && fly deploy --remote-only
```

`--remote-only` builds on Fly's builder (flyctl's default). The image is `node:24-slim` with `npm ci --omit=dev` and `src/` copied in. `server/.dockerignore` leaves out `node_modules`, `data` (the local dev database and game recordings), `test`, `*.log`, `fly.toml` and `.gitignore`. The image runs `node --disable-warning=ExperimentalWarning src/index.ts`. Node 24 strips the TypeScript types itself and has `node:sqlite` built in, so there is no build step. It runs as root on purpose, because Fly mounts volumes root-owned and a non-root user couldn't write to `/data`.

What a deploy looks like: Fly sends SIGTERM to the running machine. The server logs `[shutdown] SIGTERM`, closes the HTTP server, closes SQLite cleanly and exits. With `strategy = "immediate"`, the machine is replaced in place, and open apps lose their WebSocket for a few seconds and reconnect.

Why it's configured the way it is (`fly.toml`):

- **Exactly one machine, never auto-stopped.** The live poller and all WebSockets live in one process, so it must never be stopped for idleness, and there must be exactly one machine (`fly.toml`'s own comment). `auto_stop_machines = "off"`, `auto_start_machines = true` and `min_machines_running = 1`.
- **SQLite on a 1 GB volume** at `/data`. `HW_DB = "/data/hatewatch.db"` in `[env]`, and the `hatewatch_data` mount with `initial_size = "1gb"`.
- **A 120 s health-check grace period** for the first-boot roster ingest (measured locally at 16 s). The check is `GET /health` every 30 s with a 5 s timeout. `fly.toml`'s own comment puts the first boot, with every image verified, at about 30 to 60 s.
- **`HW_DEV` unset**, so `/dev/simulate` returns 404. `server/src/api.ts` only adds that route when `HW_DEV` is `1`.
- **Clean shutdown on deploy.** The server stops on SIGTERM and closes the database cleanly.
- **HTTPS only**, on internal port 8080 (`PORT = "8080"`, `force_https = true`).
- **Connections, not requests, are what's counted** (`type = "connections"`, soft limit 2,000, hard limit 2,500), because each open app holds one WebSocket.
- **One `shared-cpu-1x` VM with 512 MB** in `iad` (US East), the region closest to ESPN's API and most US users.

### App Store Connect answers

**In short:** these are the answers given in App Store Connect's privacy and app information forms. Hate Watch collects a random device id and what each install tracks, links both to that install, uses them only to make the app work, and tracks no one. The privacy policy and support pages are served by the server itself, and an install deletes all its data from Settings. The answers have to match what the server stores. When that changes, they are checked again against Apple's current questionnaire.

| Field | Value |
|---|---|
| Privacy Policy URL | https://hate-watch-api.fly.dev/privacy |
| Support URL | https://hate-watch-api.fly.dev/support |
| Data collection | **Yes** |
| Identifiers → Device ID | App Functionality · linked to the user · not used for tracking |
| Usage Data → Product Interaction (tracked teams/players, alert settings) | App Functionality · linked to the user · not used for tracking |
| Tracking | **No** |
| Account deletion | In-app: Settings → Delete all my data (`DELETE /me`) |

Where each answer comes from:

- **The two URLs** are pages the server renders itself (`GET /privacy` and `GET /support` in `server/src/api.ts`, their HTML in `server/src/pages.ts`). A server deploy changes them, with no app build needed.
- **Device ID:** the app creates a random device id (not Apple's or Google's advertising id) and a secret key on first launch. The server stores the id with the platform and, if notifications are allowed, the push token. The privacy page lists these.
- **Product Interaction:** the teams and players an install tracks, and its notification settings (alert types, leagues, mutes, quiet hours and their time zone), decide which alerts it gets. Its alert feed is kept to show its history.
- **Tracking: No.** There are no ads, no advertising ids, and no analytics or tracking SDKs. Shared alert links carry nothing about the device that shared them.
- **Account deletion:** Settings → "Delete all my data" asks first ("Delete everything"), then calls `DELETE /me`. That deletes the device's row, and with it its follows and feed (foreign keys in `server/src/db.ts`), forgets the device in memory and updates the live engine. There's no account to sign up for, so there's no other place to delete one.
- **Tips** are bought through Apple and Google, and the server never sees the payment ("Donations (in-app tips)" below), so they aren't collected data.

The contact email on those pages comes from `HW_CONTACT_EMAIL` in `server/fly.toml`. Double-check these answers against the current App Store Connect questionnaire. The answers are your responsibility as the publisher.

### Donations (in-app tips)

**In short:** Settings → **Support Hate Watch** has a Donate button that offers three tip sizes, sold as **consumable in-app purchases** through [`expo-iap`](https://openiap.dev/docs/setup/expo) (`app/src/lib/tips.ts`, `app/src/components/TipJar.tsx`, `TipJarStore.tsx`). Tips unlock nothing, can be bought again, and never touch our server: Apple and Google handle the payment. They work only in development and store builds; in Expo Go and on web the button explains that instead. Before they work, App Store Connect and Google Play need the agreements and the three products below.

Apple allows "tipping the developer" through in-app purchase in every country (guideline 3.1.1); external payment links would only be allowed on the US App Store.

**What you see** (`DonateCard`): a card under the "Support Hate Watch" heading with a red "Donate" button (with a heart) and under it "Servers cost money and I'd like to keep the app ad free!" (a non-breaking space keeps "ad free!" together).

**In a store or development build** (`TipJarStore`, used when `iapAvailable`):

1. When the store connection is up, the app asks it for the three products (`fetchProducts`, type `in-app`).
2. Tapping Donate swaps the button for one button per product the store returned, each with its emoji (coffee, pizza, trophy) and the store's localized price (`displayPrice`), and "Maybe later" under them, which puts the Donate button back.
   - If no product came back: "Donations aren't available right now. Please try again later." when the store is connected, or "Can't reach the App Store right now. Please try again in a moment." when it isn't.
3. Tapping a price starts the purchase (`requestPurchase`: `apple: { sku }`, `google: { skus: [sku] }`). That button shows a spinner and the others fade and can't be tapped until it's over.
4. On success (`onPurchaseSuccess`, for these three product ids only) the app finishes the transaction as consumable (`finishTransaction({ isConsumable: true })`), which lets the same tip be bought again and stops Android's automatic refund after 3 days for an unacknowledged purchase. Then a success haptic and "Thank you!", "You just helped keep Hate Watch running, and ad free." The same callback fires on launch for a tip that was paid but never finished (the app was killed mid-purchase), so it gets finished then.
5. Cancelling says nothing. Any other failure: "Donation didn't go through" with the store's message, or "Please try again."

**In Expo Go and on web** (`TipJar`): there's no store to pay through, and importing `expo-iap` without its native module crashes the app, so `iapAvailable` (`Platform.OS !== 'web'` and `requireOptionalNativeModule('ExpoIap')` present) decides first, and `TipJarStore` is only `require`d when it's true. Otherwise the Donate button shows "Donations work in the App Store and Google Play versions of Hate Watch." (a system alert, or the browser's).

**Setup in the app:** `expo-iap` is a dependency (`^5.8.2` in `app/package.json`) and a config plugin in `app/app.json`.

The product IDs are defined in `app/src/lib/tips.ts` (`TIPS`, in this order on screen):

| Product ID | Suggested price | Shown as |

| `com.hatewatch.app.tip.coffee` | $1.99 | coffee |
| `com.hatewatch.app.tip.pizza` | $4.99 | pizza |
| `com.hatewatch.app.tip.trophy` | $9.99 | trophy |

The prices are set in App Store Connect and Google Play, not in the app; the app always shows the store's localized price.

(`tip.small`, `tip.medium` and `tip.large` are burned: they were created as Non-Consumable, and App Store Connect can't change a product's type or reuse a product ID.)

1. **App Store Connect:** accept the **Paid Apps Agreement** and fill in tax and banking (Business → Agreements). Apple requires this even for free apps that sell in-app purchases.

## Data: rosters, duplicates, and images

**In short:** Every team and player comes from ESPN's public API. The server reads it all again every 6 hours (`ingest()` in `server/src/catalog.ts`), and right away when what the read collects changes (`INGEST_VERSION`, now 5). Players are deduplicated twice: on ESPN athlete id, then on normalized name plus birth date. Nothing is committed with a duplicate key or a player without an image, and every photo and game-league logo is fetched to check it exists. A player ESPN has no photo for shows their team's logo with their jersey number, never someone else's face. F1 constructors, which have no logos on ESPN, get a drawn badge instead.

Teams and rosters come from the ESPN endpoints documented in [pseudo-r/Public-ESPN-API](https://github.com/pseudo-r/Public-ESPN-API): `site.api.espn.com/apis/site/v2/sports/<sport>/<league>/teams?limit=100` and `/teams/{id}/roster` (`urls` in `server/src/leagues.ts`). They cover the **NBA, WNBA, MLB, NFL, NHL, Formula 1 and the Premier League (EPL)**. The UFC and college football are read their own way (below). The NHL is included because several of the requested alerts are hockey alerts. ESPN files soccer leagues under a code rather than a name: the EPL is `soccer/eng.1`, and college football is `football/college-football`. That code is kept as `slug` in `LEAGUES`, and every ESPN URL goes through it (`path()` in `leagues.ts`). The catalog's keys are `team:<league>:<espnId>` and `player:<league>:<espnId>` (`teamKey`, `playerKey`), so the same ESPN id in two leagues is never one row.

**The latest full ingest** was on the development database on 2026-10-11 at 18:01 UTC, with `INGEST_VERSION` 5. Its report is the `ingest:report` row in `kv`, which `GET /catalog/report` serves. It has **309 teams and 6,980 players**, 203 of them added from injured lists. It noted no problems. These are the development database's counts; production's aren't checked here. The README's previous count, from the ingest of 2026-10-06, was 150 teams and 5,505 players (seven leagues then).

**How an ingest runs, step by step** (`ingest()` in `catalog.ts`). The leagues go one at a time, in `LEAGUE_IDS` order:

1. **Teams.** It reads the league's team list and drops inactive teams (`isActive: false`) and All-Star teams (`isAllStar`). It dedupes teams on ESPN id, then on abbreviation as a second guard, noting `<league>: duplicate team <name> dropped`.
   - The logo is ESPN's `default` logo (not its dark one). If there isn't one, it's `a.espncdn.com/i/teamlogos/<league>/500/<abbrev>.png`.
   - The dark-mode logo (`logoDark`) is ESPN's `dark` one, when it has one; 296 of the 309 teams do.
   - The team colour and second colour come as hex with a `#` added: the Houston Astros are `#002d62` and `#eb6e1f`.
   - Every logo is fetched, eight at a time (`mapLimit(…, 8)`), to confirm it exists and record its size. A team without a logo stops the whole ingest ("refusing to ingest a team without an image"), so the old catalog stays.
2. **Rosters,** six teams at a time. MLB, NFL and NHL rosters group players by position (`{ position, items }`), and the NBA's is a flat list. Both are flattened.
3. **Injured lists.** It reads the league's injury report and adds anyone on it who isn't on a roster (`injuredOffRoster`), under the team the report lists them with. A player's id comes from the report's athlete, or from the `/id/<n>` in their player-card link. A report group whose team isn't in the league's catalog is skipped. If the report fails to load, the ingest carries on with the rosters alone.
4. **Dedupe** on ESPN id, then on normalized name plus birth date (details below).
5. **Players,** 24 at a time. Each gets a key, name, short name, main position, every position (`positionsOf`), jersey and team. Then its image is checked (details below).
6. **Checks before anything is written.** Every team and player key must be unique across all leagues ("duplicate key after dedupe"), and every player must have an image with a width ("player without image"). Either failure throws, and nothing is written.
7. **One transaction.** Teams are upserted (`ON CONFLICT(key) DO UPDATE`), so a team is never deleted. Players are replaced: `DELETE FROM players`, then every player is inserted again. A player who has left every roster leaves the catalog. Their follows are kept, so they come back if they're signed again.
8. **Afterwards.** It saves the report to `kv` as `ingest:report`, along with the UFC's weight classes and belts (`ufc:weight-classes`, `ufc:belts`) and college football's conferences (`cfb:conferences`). Then it reloads the in-memory catalog and the search index (`loadCatalog()`).

The log line for each league reads, for example, `[ingest] MLB: 30 teams, 1303 players (182 from injured lists, 1257 headshots, 46 logo fallbacks, 0 dupes removed)`.

- **EPL players mostly show their club crest.** ESPN has photos for only a few Premier League players (38 of 585), so the rest get the crest. That's the same accuracy-first fallback as call-ups elsewhere. Soccer headshots are all in one folder, whatever the league (`a.espncdn.com/i/headshots/soccer/players/full/<id>.png`). The EPL's injury report added nobody (0 in the 2026-10-11 ingest), so EPL rosters are ESPN's rosters alone.
- **Every position played.** A roster entry has its main position and `positions`, every one ESPN lists them at this season. Shohei Ohtani is DH, P and SP. Miguel Rojas, who has pitched mop-up innings, is 2B, RP, P, 1B, 3B, SS, DH and PH. `positionsOf` in `catalog.ts` puts the main position first and drops repeats, and returns null when ESPN lists none. The list is stored comma-separated as `players.positions` (`"DH,P,SP"`). It decides which alerts fit a player: a pitcher's alert settings have no hitting alerts, and a skater's no goalie alerts (`server/test/positions.test.ts`). `INGEST_VERSION` 3 rebuilt the catalog to read it.
- **Injured lists too.** A player on MLB's 60-day IL comes off the 40-man roster ESPN serves, and NHL players on long-term injured reserve are left off too. So Carlos Correa wasn't on the Astros. The ingest also reads each league's injury report and adds anyone on it who isn't on a roster to the team it lists them under (`injuredOffRoster` in `catalog.ts`), with the same duplicate checks and headshot verification. A player on the 10-day IL, like Cristian Javier, is still on the 40-man roster and isn't added twice (`server/test/catalog-injured.test.ts`). NBA and NFL rosters already include their injured players: the first real run added 189 MLB players, 25 NHL players and none for the NBA or NFL (commit d7c1087, 2026-10-06).
- **Refreshes every 6 hours, counted from the last one** (`INGEST_EVERY_MS`, `nextIngestIn`). Deploys restart the server, and a timer that started over on each restart kept putting refreshes off. Now the server reads when the last ingest ran and waits only what's left. In the test, a deploy at 16:00 UTC after an ingest at 12:50 waits 2 hours 50 minutes, keeping the 18:50 refresh. An overdue refresh runs at once. After that first refresh, one runs every 6 hours (`setInterval` in `index.ts`).
- **`INGEST_VERSION` rebuilds right away.** A change to what the ingest collects bumps `INGEST_VERSION`. A report from an older version (or from before versions existed) makes the next boot rebuild in the background at once. The versions so far:
  - 2: injured lists (commit 8292ab3, 2026-10-06)
  - 3: every position played (967a823, 2026-10-07)
  - 4: UFC weight classes (7443305, 2026-10-10)
  - 5: college football (9fca8a2, 2026-10-10)
- **A failed refresh keeps the old catalog.** The server logs `[ingest] refresh failed, keeping previous catalog`, and nothing is written, because the write happens only after every league has been read. F1, the UFC and college football are read in steps of their own. If one of them fails, that league keeps the rows it already has and the failure becomes a note in the report, without stopping the other leagues. This came after a deploy on 2026-10-10 at 15:06 UTC: ESPN's F1 entry list was a 404 before the grid was out, the whole refresh failed, and the new college football teams didn't arrive (commit f970f7b). Any other league's failure, such as a team list that won't load or a missing logo, still stops the whole refresh.
- **A missing league is read on boot.** If any league in `LEAGUE_IDS` has no teams in the catalog, the server starts a full ingest in the background right away. That's how F1 arrived on the existing server, and later the WNBA, the UFC and college football. An empty catalog is read before the server listens (see Run it).
- **No duplicates.**
  - Players are deduped on ESPN athlete id first. The first entry is kept, and the rest are noted: `<league>: <name> (<id>) listed on HOU and …; kept first`.
  - Then a second pass catches one person under two ESPN ids: the same normalized name and the same birth date (`dateOfBirth`). It applies only when ESPN gives a birth date. `normalize()` removes accents, lowercases, and turns anything that isn't a letter, digit or space into a space, so "José Ramírez" and "Jose Ramirez" match.
  - Teams are deduped on id and abbreviation.
  - The ingest throws rather than commit a duplicate key, and the database primary keys (`teams.key`, `players.key`) enforce it again.
- **Every team and player has an image.** The ingest won't commit a player without one ("player without image"), or an NBA, WNBA, MLB, NFL, NHL or EPL team without a logo it has fetched. College football's logos aren't fetched (they're all 500×500 on ESPN), and the UFC's and F1's teams use drawn badges.
- **Images are checked for accuracy.** A headshot is ESPN's own URL from the roster, or `a.espncdn.com/i/headshots/<league>/players/full/<id>.png`. Two checks are logged as problems in the report, but neither stops the ingest. A headshot URL must contain that athlete's own ESPN id (`/<id>.png`), and ESPN's alt text must match the player's name after `normalize()`; the mismatches are counted in `headshotAltMismatch`, and there were 0 in every league. Every image is fetched to confirm it exists and to record its true pixel size (`probePng` in `server/src/espn.ts`).
  - It asks for only the first 32 bytes (`Range: bytes=0-31`), checks the PNG signature, and reads the width and height from the IHDR header (bytes 16 and 20).
  - A 404, or a response that isn't an image, means no photo. Other failures are tried 3 times, 8 seconds each, with waits of 0.3, 0.6 and 1.2 seconds. After that the image counts as missing too, which is why the audit below checks every fallback again.
- **No wrong faces.** When ESPN has no photo for a player (practice squads and call-ups, mostly), the player gets their team's logo, never a guess (`imageKind: 'team_logo'`). In the 2026-10-11 ingest that was 103 players across the NBA, WNBA, MLB, NFL and NHL. The app draws them as the **team logo plus a jersey-number badge** in the team's colour (`app/src/components/Avatar.tsx`).
- **Images are scaled properly.** The app asks ESPN's image combiner (`a.espncdn.com/combiner/i?img=…&w=…&h=…`) for exactly the pixels it draws: the size in points times the screen density (`PixelRatio`), at the image's native aspect ratio, and never larger than the source (`sizedImage` in `app/src/lib/images.ts`). That matters because sizes vary. In the 2026-10-11 catalog, 6,313 headshots are 600×436, 2 are 600×600, and one NFL logo is 4096×4096. Every other ESPN logo in the catalog is 500×500. Headshots use cover with top anchoring, so faces aren't cropped. Logos use contain, so the whole mark shows, with ESPN's dark-mode variant when it exists. Only ESPN images go through the combiner. A `badge://` image is drawn by the app.
- **Search** comes from the same catalog (`search()` in `catalog.ts`). Names are normalized the same way. An exact match scores 100, a prefix 80, every word matching the start of a word 60, and a match anywhere else 30. Teams get 5 points more, so a team comes before a player with the same score. Teams that aren't listed (the UFC's placeholder) are left out.
- **The image switches** (`images.headshots`, `images.logos`) take ESPN's photos and logos out of everything the server sends, without a build. A team or player then gets a `badge://hidden` image, which the app draws as a badge in the team's colour with its code, and a player's jersey number (`withoutImages` in `server/src/images.ts`; CLAUDE.md has the commands). The catalog itself keeps its images.
- **The UFC** (ESPN's `mma`) has no rosters. Its fighters come from the UFC cards on ESPN's scoreboard, read a month at a time, from 24 months back to 3 months ahead (`ingestUfc`). Each fighter's weight class is the one from their latest fight, and the Contender Series is left out. Fighters need a team, so they all belong to one placeholder, "Ultimate Fighting Championship" (`UFC_TEAM`), which no list or search shows. Its logo is a UFC badge in the UFC's red (`badge://ufc`). A fighter who already has a checked photo keeps it; only new fighters, and those still without a photo, are checked again. The details are in `server/src/ufc.ts` and `ufc-classes.ts`.
- **College football** is teams only: the FBS (ESPN group 80), read from its conferences, with no rosters and no logo checks (ESPN's are all 500×500), in about 24 reads (`ingestCfb`). A read that finds fewer than 100 teams is treated as a bad read, and the teams already in the catalog are kept. Its season starts in July (`cfbSeason`). The details are in `server/src/cfb-poll.ts`.

**Formula 1 is different** (ESPN sport `racing`, league `f1`):

- **Drivers** are the ones who actually raced this season: the championship standings plus this weekend's entry list. The season's athlete list also includes reserves.
- **Team and car number** come from this weekend's entry list. ESPN's athlete records can be stale after a team move: Lindblad's record says "Red Bull #36", but he races the Racing Bulls #41. The record is only the fallback, for a driver who isn't entered (e.g. Tsunoda, replaced mid-season).
- **Which entry list:** the latest session of the weekend whose entry list ESPN serves. A race's list is a 404 until its grid is out (the evening after qualifying), even though the scoreboard already lists its cars. If no session's list loads, the athlete records alone decide (`ingestF1` in `catalog.ts`).
- **A driver whose team matches no constructor** is skipped and noted in the report ("matches no constructor; skipped"), rather than put on the wrong team.
- **Constructors have no logos on ESPN** (404, `logos: null`). Rather than use trademarked logos from elsewhere, the app draws a badge in the team's official ESPN colour with a code, with black or white text for contrast. The colour falls back to grey (`#888888`) when ESPN has none. The image is `badge://f1` (`F1_BADGE`), and the codes are `F1_CODES`: ALP, AMR, AUD, CAD, FER, HAA, MCL, MER, RB, RBR, WIL. The text colour is whichever reads better on the team's colour (`readableOn` in `Avatar.tsx`): dark on Alpine's yellow (`#FFF500`) and Williams' white, white on Ferrari's red. Drivers without an ESPN headshot (8, all re-checked as 404) get that badge plus their car number. In the 2026-10-11 ingest they were Antonelli (12), Bearman (87), Bortoleto (5), Colapinto (43), Hadjar (6), Lawson (30), Lindblad (41) and Piastri (81).

Audit it yourself: `cd server && node test/verify-catalog.ts`.

It reads the database at `HW_DB` (by default `server/data/hatewatch.db`) and prints:

- duplicate player keys, and duplicate ESPN ids within a league
- players with the same name on the same team
- players without an image, and teams without a logo
- every headshot size and logo size, with how many of each
- headshots whose URL isn't keyed by the player's own id
- every logo fallback checked again against ESPN with a `HEAD` request, as a tally of status codes. Every one should be a real 404, not a network failure.

It opens the database through `db.ts`, as the server does, so an older database gets any missing tables and columns added, the same as on a server start.

## Real-time: how fast is it?

**In short:** An alert reaches an open app within milliseconds of the server seeing the play, and a closed phone typically 1-3 seconds later through Expo's push service. Nearly all the delay before that is ESPN's: it posts a play well after it happens, so each live game's feeds are read every 2 seconds with ESPN's CDN cache bypassed. A few alerts wait on purpose, for ESPN to finish a review or a half-inning, and football alerts are revised when ESPN changes a play after posting it. The tables below give every stage and every deliberate wait, with the constant and environment variable behind each.

| Stage | Latency | Where |
|---|---|---|
| ESPN publishes the play | **~80–105s after it happens** (measured live on MLB when the server was first built; upstream, not ours) | ESPN |
| Our poll interval | 2s per live game (`HW_LIVE_POLL_MS`), longer only when a poll itself runs long (below) | `GameTracker.loop` in `live.ts` |
| ESPN's CDN cache | bypassed on every live read (it would add up to 10s) | `getJson(…, { bust: true })` in `espn.ts` |
| Detection + fan-out + WebSocket | <10 ms (WebSocket delivery measured at 1 ms locally; `test/smoke.ts` prints it) | `publish()` in `fanout.ts` |
| Push via Expo → APNs/FCM | typically 1–3s | `sendPushes` in `push.ts` |

**What production measures.** Every alert published writes a log line such as `[event] mlb.team.down_in_order → team:mlb:5: Guardians went down in order (lag 13.5s, 2 followers)` (`publish` in `fanout.ts`). The lag runs from ESPN's own timestamp on the play (its `wallclock`, kept as `NPlay.at`) to the moment the server published the alert, so it measures ESPN's posting delay plus ours from the time ESPN stamps, not from the moment the play happened, and it isn't the same number as the ~80–105s above. Alerts built when they're published (a final, a box-score fact, a standings drop) log 0.0s. On production during ALDS Game 5 (White Sox at Guardians, October 10 2026, in `server/data/recordings/mlb-401907994-prod.log` on the Mac), the 19 MLB alerts tied to a play had lags from 10.9s to 92.7s, median 23.9s. The longest were held on purpose: "Guardians lost an ABS challenge" logged 92.7s, most of it the ABS hold below.

**How a game gets tracked.**

- **Scoreboard scans.** The engine (`LiveEngine` in `live.ts`) reads every league's ESPN scoreboard every 10s (`HW_SCOREBOARD_MS`, `scanScoreboard`), cache-busted, with a 6s timeout. Every game on it gets a Scores tab card. College football's scoreboard lists every FBS game, a big read, so it's read every 20s (`HW_TEAMS_ONLY_SCOREBOARD_MS`), and only once in 5 minutes while no game is live or starting within 20 minutes.
- **Which games.** A game is tracked when someone tracks either team: the teams people follow, plus the teams of the players they follow (`watchedTeamKeys`, cached 3s). Its tracker (`GameTracker`) starts when the game is live, or within 3 minutes of its start (`startsIn < 3 * 60_000`). A game seen before its start is remembered (`preSeen`) until its tracker starts, even if it goes live early, as a doubleheader's second game can. The log says `[<league>] tracking <ESPN's short name> (<event id>)`.
- **"Hate Watch Starting".** A game the scanner saw before it started (`preSeen`, passed to the tracker as `sawPre`) gets its start alert when the tracker sees ESPN flip it from `pre` to `in`. A game first seen already under way (a follow in the 3rd quarter, a server restart) never gets one.
- **Following mid-game.** Following or unfollowing someone (`PUT` and `DELETE /me/follows/:key` in `api.ts`, and "Delete all my data") calls `engine.kick()`. That clears the watched-teams cache and runs every league's scoreboard scan, F1's and the UFC's, and Up next at once, so a game already on starts tracking on that scan. If a scan is already running, the kick does nothing extra (`every()` skips a run while one is in flight), so the worst case is the next regular scan, up to 10s later.
- **Stopping.** When nobody tracks either team any more, the tracker stops (`stopped tracking … nobody tracks either team now` in the log). At the final it finishes (the loss alerts, `finish`) and stops. Whichever sees the final first finishes the game, the tracker's poll or the scoreboard scan (`finish` runs once). When a tracked team's game is final on the scoreboard with no tracker at all (a restart just after the buzzer), the scan creates one just to finish it, if the game started less than 6 hours ago.
- **History on attach.** When a tracker first reads a game, plays older than 90 seconds by ESPN's timestamp (`BACKFILL_WINDOW_MS`) update its state (the score, bases, who's in goal) but never alert, and box-score alerts are skipped on that first read. So following a team in the 7th inning doesn't replay the first six. The rest of what the tracker remembers is in [docs/duplicate-alerts.md](docs/duplicate-alerts.md), Layer 3.

**Each poll** (`GameTracker.poll` in `live.ts`):

- **Two sources per game, read in parallel** (`Promise.allSettled`): ESPN's *core* plays endpoint (`urls.corePlays`, logged as the `plays` feed) and the *site* summary (`urls.summary`, the `summary` feed). They're merged by play ID, which is identical across both (`mergePlays` in `detectors.ts`): the core list is kept in its own order, never sorted, a play in both is the core copy, and a play only the summary has is slotted in right after the last play the two share before it. Measured live, core publishes plays **~18s sooner** than the summary (the code's comment says 15-20s). The detectors give identical results on both sources: `test/core-vs-site.ts` runs three finished games (MLB 401907973, NHL 401891781, NBA 401811026) through each feed and the merge, and `logic.test.ts` checks the merge keeps play order.
- **Which leagues read what.** MLB, the NBA, the WNBA and the NHL read both feeds as above. **The NFL** reads its plays from core alone: its summary has drives without participants, so it's used for the game's status, the header's score, the drives and the box score. **College football** reads the summary alone, its plays from the drives (`fromDrivePlays`), every 5s instead of 2s (`HW_TEAMS_ONLY_POLL_MS`), because its summary is big and a Saturday has dozens of games. **Soccer** reads the summary alone: its key events (`fromKeyEvents`: goals, cards, penalties, substitutions) are the plays and its commentary gives the fouls (`fromCommentary`); the core touch-by-touch feed is read every 10s (`HW_TOUCH_MS`), a page of 100 at a time, only while someone tracks a player in the match (`readTouches`). F1 and the UFC have their own engines: F1's is under "F1 how" in Notifications, the UFC's in `ufc.ts`'s header comment and `PATCH_NOTES.md`.
- **One feed failing.** If one read fails, the other's plays are still used. The summary carries the game's status, so while it's failing the start alert, box-score facts and win probability wait for it (a final can still come from an "End of Game" play, or from the scoreboard). If every feed the league uses fails, the poll throws and logs `poll error`.
- **The CDN cache is bypassed.** ESPN's CDN caches these endpoints for up to 10s (`max-age=10`). Live reads add a unique query parameter (`_hw=<time>`, the `bust` option of `getJson` in `espn.ts`), and measured live on an MLB game, that surfaced every new play **4–10s sooner (avg 6.7s)**. Conditional requests (an ETag, answered 304 from the cached body) are only for reads that aren't busted, such as the injury reports; a busted read never sends one.
- **Timeouts and retries.** Each read of a live game's feeds has a 4s timeout (`timeoutMs: 4000`). `getJson` tries up to 3 times, waiting 250, 500 and 1,000 ms after each failure (a 404 stops at once), so a feed that's down can hold a poll for about 14 seconds before it gives up.
- **Slow reads are logged.** A read over 3s (`SLOW_READ_MS`) logs `[<league> <game>] summary read took <n> ms`; a failed one logs `plays read failed after <n> ms: <error>`, naming the feed. This came from ALDS Game 5, where one alert went out 26 seconds late with nothing in the log, and 8 polls had both feeds over 4s.
- **Polls don't overlap.** The next poll starts 2s after the last one *started* (`Math.max(250, LIVE_POLL_MS - lastPollMs)`). When a poll takes longer than 1.75s, the next starts 250 ms after it ends. `GET /health` lists every tracker with its `lastPollMs` (`engine.status()`), the quickest way to see a slow game on production.

**Everything the server reads on a timer.** The engine's scans run through `every()` in `live.ts`, which never starts one while the last is still running; the game polls, the clips after a final and the notice check have their own loops:

**Alerts that wait on purpose.** Most alerts go out on the poll that first sees their play. These wait, because going out at once would sometimes be wrong:

| Alert | Waits | Setting | Why |
|---|---|---|---|
| MLB: a lost ABS challenge | until a later play exists and 60s have passed (at the final, at once); a pitch missing from the feed must be missing two reads in a row | `HW_ABS_SETTLE_MS` | ESPN posts every challenged pitch "Confirmed" first and swaps in "Overturned" later (three wrong alerts on October 7, 2026; overturns took 10 and 15s in ALDS Game 5). `holdAbs`, `test/abs-settle.test.ts` |
| MLB: a half-inning's end (down in order, stranded runners, NOBLETIGER) | the first read with the "End of the inning" play and the third out, 20s at most | `HW_HALF_END_WAIT_MS` | a stale read can have one without the other (`halfInningEnds`, `test/half-end-wait.test.ts`) |
| MLB: an at-bat's result posted without its batter | until the batter is on it, 20s at most | `HW_HALF_END_WAIT_MS` | it can't be pinned on anyone yet (`waitForBatter`) |
| MLB: being no-hit through 6 | until the box score agrees on zero hits | | the core feed's hit count can run ahead |
| MLB: the pitcher's loss | the summary every 15s, up to 20 times (5 minutes), until ESPN posts the W/L | `HW_DECISION_RETRY_MS` | the decisions trail the last out (`finalPitching`) |

**Ways the delay is kept down, and alerts kept right:**

- **No duplicates or stale floods.** Each event has a deterministic ID (`game:play:type:athlete`), so re-polls, restarts and overlapping sources never double-notify. Plays from before the server attached to a game aren't announced. Every layer of this (ids, storing an id once, the tracker's memory, one alert per moment, ESPN's edits, what a restart forgets) is in [docs/duplicate-alerts.md](docs/duplicate-alerts.md): read it before changing alert code.
- **ESPN edits plays after publishing them, and scoring alerts allow for it.** A goal can be marked as scoring only after it first appears, and a disallowed goal is taken back. So each poll re-derives the score from every play (`nextScore`) instead of keeping a running total. Team alerts go out once per score each side reaches (`announced` in `GameTracker.poll`):
  - A goal flagged late still alerts when the flag appears, logged as `late score: play … became a scoring play after it was first published (<away>-<home>)` (on production on October 10, 2026: `[nba 401898396] late score: play 401898396144 became a scoring play after it was first published (24-28)`). In the NHL, that late goal also gets the goalie's "let one in" alert.
  - A goal that was taken back is logged as `score went down to <away>-<home> (a goal taken back?); the next one is news again`, and that team's next goal is news again.
  - A goal only visible through the next one (a 2-1 play right after 1-0) alerts for both teams, once.
  - Checked by playing tonight's four NHL games plus MLB, NFL and NBA finals back through the real tracker a few plays per poll (2026-10-05): every scoring play reached the other team exactly once. `test/live-score.test.ts` drives a real `GameTracker` through these cases with plays shaped like ESPN's (WPG @ PIT, 2026-10-05).
  - The tracker also logs when it stops because nobody tracks either team.
- **Football plays ESPN changes after it posts them** (`revisions.ts`, `GameTracker.poll`). Alerts still go out the moment a play is first seen: nothing waits for a review. In October 10 2026's twelve noon college games ESPN edited 49 plays in place (about 30 gained a flag; an interception became roughing the passer), took out or re-posted 31 (touchdowns and turnovers overturned on review, one touchdown posted under three ids), and changed drives' results after they ended. So each play and drive keeps the alerts it sent for 15 minutes (`REVISE_MS`), and each read compares them with what ESPN says now:
  - An alert the play no longer has gets a line on it, with no push: "Wiped out by a penalty on Indiana: Roughing The Passer.", "Overturned on review.", "ESPN has since changed how the drive ended: End of Half."
  - One it has now goes out then: a flag added later (feed only, as flags are), an incompletion that became an interception, the turnover on downs a review left.
  - A play re-posted under a new id at the same spot (the same period, a start within 10 seconds, the same player: `samePlay`) is that play, not a new one; one gone from the feed for 30 seconds (`GONE_MS`) is gone (a read can come back short).
  - A score is taken back only when the plays, the score the latest plays carry and the header all agree, two reads running; its alerts get a line, and the same side scoring on that drive within 10 minutes (`RESCORE_MS`) is another line on them ("Then Wake Forest scored on the same drive: WAKE 16, NCSU 14."), not a second alert. An extra point never alerts on its own.
  - When the drives lag the score by minutes (Missouri's last touchdown against Texas A&M never reached them), the header's score a minute ahead of the plays, while they trail its game clock, sends the score alert without its play.
  - An "End of Game" play ends a football game only after a 4th-quarter play (ESPN put one after the 3rd quarter at Missouri, then took it out).
  - Lines reach a device through the alert it got for that play, kept in memory for 6 hours (not across a restart).
  - Checked by replaying that day's recording as the server read it, poll by poll, and in `test/play-revisions.test.ts`.
  - The NFL's core plays go through the same code. Checked against the finished games of the 2026 season's first five weeks (a live NFL recording is still to come): ESPN marks a play wiped out by a penalty "- No Play." but keeps its type 73 times in 734 (sacks, incompletions, a strip-sack), so a wiped-out play alerts only its flags; after a review that reversed a call ESPN keeps the overturned call in front of "the play was REVERSED.", and what stands is the call after it (a pass interference that had wiped out an interception, itself overturned).
  - An alert taken back that its play has again (a flag overturned on review, a play back in the feed, a re-post) gets a line on it ("Overturned on review: it stands.", "ESPN has since put this play back."), never a second alert.
  - A flag's alert taken back while its play stands says what became of the flag: "ESPN has since charged this flag to Robert Hainsey." (a device that had the first player's alert gets that line, not the new player's flag as a second alert) or "ESPN has since taken the flag off." (Eagles at Jaguars, October 11 2026).
  - How the revisions ledger works, and what it can't do after a restart, is in [docs/duplicate-alerts.md](docs/duplicate-alerts.md), Layer 5 and "What survives a restart".
- **Feed order is by when it happened.** The feed is ordered by ESPN's wallclock time for the play, not by arrival time.
- **Pushes never hold up anything.** `publish()` writes the feed rows and WebSocket frames first, then hands the pushes to `sendPushes` (`push.ts`), which posts them to Expo in chunks of 100 without waiting for the answer (10s timeout). Each push is `priority: 'high'` and `interruptionLevel: 'time-sensitive'` on the `hate-events` channel. A token Expo reports as `DeviceNotRegistered` is cleared, so a deleted app stops costing a request.

**The remaining floor is ESPN's own delay.** To go faster you need a lower-latency feed per league: MLB StatsAPI (`statsapi.mlb.com/api/v1.1/game/{pk}/feed/live`), NHL (`api-web.nhle.com`), NBA (`cdn.nba.com/static/json/liveData`), or a paid provider such as Sportradar. Any of these can feed the same detector interface (`NPlay`); you'd map ESPN athlete IDs to league IDs by name + team.

## Notifications (76 types, all user-controllable)

**In short:** every alert type a user can switch is one entry in `EVENT_TYPES` (`server/src/event-types.ts`): 152 types today, 99 of them pushed by default, 37 feed only (on, in the feed, no notification) and 16 off. The table below says what each league's alerts are and how they're detected. Under the table: the defaults new installs get, what older installs kept, and every control in Settings, on a player's or team's own alert screen and on the Tracking tab. A game, news or standings alert goes through `publish()` in `server/src/fanout.ts` (the weekly recap through `publishTo`; developer notices, which are never pushed, through neither). It is stored once by its id. If it's a loss, it counts on the Successful Hate Watch tally. It reaches the feed of each device that tracks its target (or one of the team's players, with "Get their team's alerts" on) and has the alert switched on, as one alert per thing that happened. It's pushed only when push is on, the target isn't muted, it isn't quiet hours in the device's stored time zone, and the bell of the alert (or of a fact folded into it) says notify. "How a push is decided", below, goes through it step by step; [docs/duplicate-alerts.md](docs/duplicate-alerts.md) covers how one thing happening stays one alert.

A new install (`POST /devices` in `server/src/api.ts`) stores `DEFAULT_PREFS` (`fanout.ts`): push on, sound on, quiet hours off (set to 23:00 to 08:00, America/New_York, until the device turns them on), and empty maps for every choice (`leagues`, `types`, `muted`, `targetTypes`, `pushTypes`, `targetPushTypes`, `playerTeams`). Only what a device chooses is stored; everything it hasn't touched is read from the type's default at the moment an alert is judged (`typeEnabled`: `types[id] ?? defaultOn`; `pushTypeFor`: the target's bell, then the Settings bell, then `defaultPush`, then push). So a default changed in `event-types.ts` reaches every device that never chose, at the next deploy, unless it's listed for keeping, below.

Installs from before a default change keep what they had. Each change of defaults so far has a one-time migration in `fanout.ts` that runs when the server boots, writes the old default into each existing device's settings wherever the device hadn't chosen (its own choices are spread over the old defaults, so they win), and marks itself done in `kv` so it never runs again; a device created after it gets the new defaults. A later default change needs its own list and its own key.

- `keepOldDefaults` (kv `prefs:quiet-defaults`, October 2026, the quieter defaults): existing devices keep `WERE_ON` switched on (Opponent has runners in scoring position, the NBA's and the WNBA's Misses a shot, every soccer league's Loses the ball) and `WERE_PUSHED` pushed (Gives up runs, No quality start, Loses a challenge, Strands runners in scoring position, Gets sacked, the NBA's and WNBA's Misses a free throw and Turns it over, Shoots and misses, Drops in the drivers' championship, Opponent scores, Falls behind, Drops in standings, Losing streak, A player gets injured, every soccer league's Commits a foul). Alerts added after it (Goes down in order, Goes hitless, Pits and the rest) were never anyone's, so everyone has their new defaults.
- `lossFactsFollowLoss` (kv `prefs:loss-facts`, October 2026): when a loss's facts became alerts of their own (Loses at the last second, Loses as the favorite, Gets shut out, Gets swept, Loses to a worse team, Falls below .500: `LOSS_FACT_TYPES`), a device that had "Loses a game" off, in Settings or for one team, got all six off too, the same way, so a loss it had silenced doesn't come back as "lost as 64% favorites".
- `keepFlagsPushed` (kv `prefs:nfl-flags-feed`, October 11, 2026): an NFL player's flag (`nfl.penalty`, "Commits a penalty") became feed only for new installs after the Jaguars' trackers got 14 pushes for 19 flags in London; existing devices keep it pushed (`FLAGS_WERE_PUSHED`).

`GET` and `PUT /me/prefs` (`api.ts`) answer with `prefsDto(prefs)`: every feed-only-by-default alert's bell filled in as off, so app builds that read a missing bell as "push" draw it right. What's stored stays only what the device chose (`test/quiet-defaults.test.ts` checks both). "Reset alerts to defaults" resets the bells too in app builds after 10 (build 11's patch notes); earlier builds reset only the switches.

Settings let users control:

- push on/off: Settings → Delivery → "Push notifications", stored as `pushEnabled`. Off, nothing is pushed to the device, while every alert still lands in the feed and reaches the open app over the WebSocket. The switch shows on only when `pushEnabled` is on and the phone's permission is granted ("Blocked in system settings — the feed still updates live." when it isn't). Turning it on without permission asks for it first (`enablePush` in `app/src/lib/store.tsx`). A device with no push token (permission never given, or Expo reported the token `DeviceNotRegistered`, which `server/src/push.ts` clears) gets no pushes either way: `publish()` pushes only to a device with a token.
- sound: "Sound", stored as `sound`. On, each push carries the default sound; off, it's sent with no sound (`sound: null`) and still shows on the lock screen. It covers the weekly recap's push too (`publishTo`).
- quiet hours in their own timezone (alerts still reach the feed): "Quiet hours", with From and Until steppers in whole hours (12 AM to 11 PM), stored as `quietHours: { enabled, start, end, tz }`. Flipping the switch (on or off) stores the phone's time zone (`Intl.DateTimeFormat().resolvedOptions().timeZone`); changing the hours doesn't, so after changing time zones, switch it off and on to pick up the new one. `inQuietHours` (`fanout.ts`) formats the time when the alert is published as "HH:MM" in that zone and compares: the start is inside, the end isn't, and a start later than the end runs over midnight. With 23:00 to 08:00 in America/Chicago, a strikeout at 11:30 PM Chicago time and one at 7:59 AM are quiet, and one at 8:00 AM pushes. With 13:00 to 15:00, only the afternoon is quiet. A start equal to the end is never quiet. A quiet alert is stored as not pushed and is never pushed later: when quiet hours end, nothing catches up. The open app still buzzes for a live alert unless its target is muted (`store.tsx`). The weekly recap's push follows quiet hours too (it still lands in the feed), and the recap goes out by this time zone ("US Eastern until you turn them on").
- each league on/off: no longer a switch of its own. Settings used to have a Leagues section, and `leagues[league] = false` from then still works: it turns off every alert of that league that the device hasn't set per target (`typeEnabledFor`), and its group in Settings is greyed out with "League off · All on turns it back on". Tapping that group's "All on" switches every alert in it on and the league back on. A target's own choices on its alert screen beat a league that's off.
- every alert type, with "all on/off" per group, **under section headings** (`section` in `event-types.ts`, in the list's order, which `bySection` in `app/src/lib/types.ts` keeps: a section is where its first alert is): the groups are "<League> alerts" for each league in the server's order (that league's own alerts), then "All player alerts" and "Team alerts" (the ones every league shares). Sections inside them: MLB Offense (with the team's "Goes down in order") · Defense · Pitching · Challenges · Team. NFL Offense · Penalties · Special teams · Team. College football Offense · Penalties · Special teams · Team · AP poll. NBA and WNBA Offense · Fouls · Team. NHL Offense · Penalties · Goaltending · Team. Soccer Attack · Defense · Cards & fouls · Goalkeeping · Lineup · Team. F1 Race · Qualifying · Championship · Team. UFC Fight. All player alerts: Game · Injuries & news. Team alerts: Game · Season · Injuries & news · Your Hate Watch. The list is written so that within a section the ones that push by default come first, then feed only, then off. Each row is the alert's emoji and name, its bell and its switch, with no explanation under it (app builds after 10; older builds show `description`); "Feed only: no notification" shows under a row that's on with its bell off. **Each group folds up**, and they all start folded: a folded group shows its alerts' emoji (six at most: five and "+N" when there are more) and how many are on, "13 of 15 on" (or "League off · All on turns it back on"). Tapping the header or that row opens it; the header folds it again. "All on" / "All off" (`setAll`) sets every alert in the group, folded or not, and reads "All off" only when every one is on. A player or team's alert screen uses the same headings, its league's first, then the shared ones (`test/sections.test.ts`), and **only the alerts that fit a player's positions**: each alert's `positions` (`only` these, or any but `not` these, in its league's ESPN codes) against every position they've played (`fitsPosition` in `app/src/lib/positions.ts`; `test/positions.test.ts`). MLB pitchers (SP, RP, P) get no hitting or baserunning alerts and hitters no pitching ones; Ohtani gets both. NFL: interceptions, sacks, incompletions, delay of game and getting pulled for quarterbacks, missed kicks for kickers (PK), fumbles for anyone but linemen, kickers and long snappers, giving up a safety for the offense. NHL and soccer: the goals against for goalies only, shots for skaters, missed penalties and losing the ball for outfield players. Basketball and F1: everything. A player with no positions known gets everything, and the screen says when some are hidden ("Showing the alerts that fit T. Skubal's positions (SP, P). 4 that don't are hidden."). Global settings still decide the hidden ones. The Your Hate Watch alerts (the streak, the weekly recap) are about the device, not one target, so they're in Settings only. Older app builds get the same order without the headings.
- **a 🔔 on every alert type: notify me, or feed only.** Off keeps that alert in the feed without a push ("Feed only: no notification" under it). The switch decides whether the alert arrives at all; the bell only decides whether it also makes a notification, so it's greyed out and can't be tapped while the switch is off. Stored as `pushTypes` (typeId → push) in prefs; missing means the type's default (`defaultPush`: push, unless it's feed only by default; see the defaults above). The same bell is on every row of a player or team's alert screen, stored as `targetPushTypes` (targetKey → typeId → push), and it beats the Settings bell for that target (`pushTypeFor`). For example, with "Gets sacked" feed only in Settings, a bell turned on for Caleb Williams alone pushes his sacks and no other quarterback's. "Custom for …", "Use global setting" and "Reset all" cover the bells too, and the Tracking tab's gear turns red for one.
- **How a push is decided** (`publish()` in `fanout.ts`), for each alert in each publish, in this order:
   1. **Who it can reach** (`recipients`): every device tracking its target, and for a team's alert, every device tracking one of that team's players with "Get their team's alerts" on, once per device. With nobody, the alert isn't stored at all, so its id stays free for when someone follows.
   2. **Stored once:** inserted into `events` with `ON CONFLICT(id) DO NOTHING`. An id already there (a re-poll, a restart, the same play from two feeds) stops here: no feed row, no live frame, no push.
   3. **Counted:** a Successful Hate Watch is recorded for every one of those devices before any setting is looked at (`recordHateWatch`), so switching "Loses a game" off doesn't stop the counter.
   4. **Delivered at all** (`shouldDeliver`): the alert's type, or any of its `aliases` (other switches that cover it), must be on for that target (`typeEnabledFor`: the target's own switch if it has one, else the league not switched off and the Settings switch, else `defaultOn`). Then an alert marked `unless: X` is dropped for a device that wants X for that target, because X says the same thing more specifically (stranded runners, `unless` the NOBLETIGER). Muting and quiet hours don't come into it: they only stop the push.
   5. **One alert per thing that happened:** a `lateOn` alert becomes a line on the device's latest alert about it when there is one (a standings drop after a loss); of a moment's `firstFollowed` alerts the device gets the one about what it followed first; of a `moment`'s alerts it gets the first it wants, and the later ones become lines on it (their `fold`), at most one per `alt` group, or are dropped. A fact that comes in a later publish, within 6 hours, becomes a line on the alert already sent, with no push. All of this is in [docs/duplicate-alerts.md](docs/duplicate-alerts.md), Layer 4.
   6. **Pushed or not** (`willPush`): the device has a push token; `pushAllowed` says yes (push on, this target not muted, not quiet hours now); if the alert reached it through a tracked player ("Get their team's alerts"), that player isn't muted; and `pushWanted` says yes for the alert or for any fact folded into it. `pushWanted` takes the first of the alert's type and its aliases that's switched on for the target and asks its bell (`pushTypeFor`: the target's bell, then the Settings bell, then `defaultPush`, then push).
   7. **Sent:** the device's feed row (`pushed` 1 or 0, the folded lines in `extra`), an `event` frame to each socket the device has open (the lines in front of the body), and if it's pushed, a notification titled with the alert's emoji and title, the lines and body as its text, the device's sound choice, and a `threadId` that stacks a team's alerts and its players' together on iOS (`pushThread`). An F1 device's alerts from one session in one publish are one notification ("Singapore GP · Sprint: 7 alerts", `bundled`).

  An alert that counts for several types follows the most specific one switched on. A homer is "Gives up a home run" with the alias "Gives up runs". With the defaults (home runs pushed, runs feed only) it pushes. With home runs' bell off, it arrives quietly, whatever the runs bell says, because the home-run switch is still on and decides. With home runs switched off, it still arrives, as a run, and pushes only if the runs bell is on (feed only by default). A device tracking Gerrit Cole and the Yankees gets one alert for a go-ahead homer off Cole, Cole's, with "Rays took the lead." as a line, pushed because Cole's homer is (`test/bundling.test.ts`); a device with only the Yankees gets "Rays took the lead over the Yankees on Caminero's 402-foot solo homer", feed only by default.
- per-target 🔕 on the Tracking tab: turns off push for that player or team, while their alerts still land in the feed. The same setting is the "Push notifications" row at the top of the target's alert screen ("Off: <name>'s alerts still show up in your feed, without a push."). Stored as `muted` (a list of target keys) and checked in `pushAllowed` by the alert's own target, so muting the Yankees quiets the Yankees' alerts but not Gerrit Cole's. It also covers a team's alerts that arrive through a muted player with "Get their team's alerts" on. A device that tracks the team itself gets the team's alerts as the team's, by the team's mute. The open app doesn't buzz for a muted target's live alerts. In a shared moment the mute of the device's own alert decides: muting Cole quiets his alert and the Yankees' line folded into it, while muting only the Yankees doesn't stop Cole's alert, carrying the Yankees' line, from pushing.
- **A team's roster, by position:** chips over the roster on a team's page filter it by position group, each with its count, only groups that have players: MLB "All 30 · Starters 7 · Relievers 7 · Catchers 2 · Infield 7 · Outfield 5 · DH 2" (the Yankees); NFL QB · RB · WR · TE · O-line · D-line · LB · DB · Specialists; NBA and WNBA Guards · Forwards · Centers; NHL Forwards · Defense · Goalies; soccer Goalkeepers · Defenders · Midfielders · Forwards (`ROSTER_GROUPS` in `app/src/lib/positions.ts`, by the position each player is listed at). F1 teams have no filter. Chips too many for one row (these, and the league filter when you track more leagues than fit) put All across the top and the rest evenly below (`ChipRows` in `ui.tsx`).
- **The league filter** (Feed, Tracking, Search, Scores, the leaderboard; `FilterBar.tsx`): All, then the leagues you track, in the server's league order, then More. Until you track anyone, the first four leagues in that order (NBA, MLB, NFL, NHL). More opens every league in a sheet (`LeagueSheet.tsx`): yours first, then the rest under their sport ("Basketball: NBA, WNBA", "Football: CFB", "Combat sports: UFC"), each sport where its first league comes in the server's order, with "Find a league" searching names, full names ("Premier League") and sports. A league picked there joins the row while it's picked; picking it again goes back to All. With every league already on the row, there's no More. So the row stays one short line however many leagues are added. A sport's heading and a league's full name are the server's (`sportName` and `fullName` in each league's `ui`, `server/src/leagues.ts`; a sport without one is ESPN's word for it, capitalized), so a new sport needs no app update.
- **A player or team's page** (from Search, the Tracking tab, a roster or the leaderboard): "Recent misery" is your alerts about them from the last 24 hours, newest first. It shows the latest one, with "Show N more" to open the rest and "Show less" to fold them back. The page asks the server for that target's day (`GET /me/feed?target=…&after=…`), since the app's loaded feed may not reach that far back, and adds alerts that arrive live while it's open.
- **Search: sort teams A–Z or by division.** With nothing typed, Search lists every team (in the league filter, or every league). "Sort teams: A–Z | By division" groups them by division, in ESPN's order: MLB "AL East", NFL "AFC South", NBA "East · Atlantic", NHL "West · Pacific", the WNBA by conference, the EPL as one table, F1's constructors together; across every league, by league first ("MLB · AL East"). Each group says how many teams are in it. From ESPN's division-level standings (`?level=3`, `server/src/divisions.ts`), kept 12 hours; `GET /teams?by=division` adds each team's `division`. The choice stays while the app is open.
- **How many people hate them:** every player and team row says how many people (devices) track them: the Tracking tab, Search results and its team list, and team rosters ("👁 12 haters", "1 hater (just you)", "No haters yet"). A player or team's own page shows it under their name. `GET /search`, `GET /teams` and `GET /targets/:key` (with its roster) carry `haters` (`withHaters` in `leaderboard.ts`). The app keeps the freshest count it has seen for each one (`noteTrackers` in the store), so tracking someone from Search bumps their number right away. A player counts on their own, not toward their team. It's a count over `follows` (indexed by target), so there's nothing extra to store. `GET /me/follows` returns `trackers` on each follow. Following or unfollowing returns the new count, so the number updates at once, and the tab reloads the counts each time it opens. Deleting a device's data removes it from every count.
- **A tracked player's team ("Their team" on the player's ⚙️ screen):** two switches. **Show their team's games** (on by default) puts the team's games in My games and Up next on the Scores tab, as tracking a player always did; off, they're left out unless you track the team or another of its players with it on (`deviceTeams` in `scores.ts`; F1 drivers don't have it, since F1 sessions show for any F1 follow). **Get their team's alerts** (off by default) sends the team's own alerts too, as if you tracked the team, by your Team alerts settings: game starts, losses, opponent scores and the rest (`recipients` in `fanout.ts`). Tracking the team itself gets both, so the switches are greyed out then.

A row you haven't touched says "Global setting (on)", "(on, feed only)" or "(off)"; one you have says "Custom for …" with "Use global setting", which clears both its switch and its bell; "Reset all N to global settings" clears every one. Stored as `targetTypes` (targetKey → typeId → on/off) in prefs; a `null` in a PUT resets one back to global, and unknown types or malformed keys are ignored (`mergeTargetTypes`). The "one alert, not two" rules (NOBLETIGER vs stranded, lead changes) use the same per-target answer.
- reset to defaults: Settings → Data → "Reset alerts to defaults" writes every alert type's switch as its `defaultOn`, every bell as its `defaultPush`, and every league as on. It leaves the per-target choices, mutes, quiet hours, sound and the push switch as they are, and asks nothing first. Because it writes values rather than clearing them, a reset device keeps today's defaults even if a later deploy changes them.
- clear feed: Settings → Data → "Clear feed" (after "Clear feed?"/"This removes every item from your feed." on a phone) deletes the device's feed rows (`DELETE /me/feed`). The alerts themselves stay stored, so they're never sent again, the Successful Hate Watch counter keeps its count, and a line that comes later for a cleared alert is dropped rather than sent as a new alert (`addLateLine`; `test/bundling.test.ts`).

A homer counts as "gives up runs" too, so turning off "gives up a HR" alone won't hide the runs: the homer still arrives, as a run (see "How a push is decided"). ## Scores tab

**In short:** The Scores tab lists games. "My games" is today's games for the teams you track and the teams of the players you track (live first, then later today, then finals, each kept for 24 hours after it ends), followed by "Up next", each tracked team's next game. "All games" is every game live now or starting in the next 24 hours, whether you track anyone in it or not. The cards come from the server's ESPN scoreboard reads every 10 seconds, with scores and details patched in sooner by the 2-second game tracker, and every change is pushed over the WebSocket to the devices that track a side; tapping a card opens its game screen, with the live card, the box score and highlights, and your alerts from that game.

**The switch at the top** (`app/src/app/(tabs)/scores.tsx`). Two segments, "My …" and "All …". The word is the server's word for what the league chip shows (`eventsWord`, from each league's `ui.events` in `server/src/leagues.ts`): "games" for the NBA, MLB, NFL, NHL, EPL, college football and the WNBA, "fights" for the UFC, and "events" with All picked, since that mixes leagues. So with MLB picked it reads "My games | All games · 3 live", and with All, "My events | All events · 9 live". The "· N live" count is how many games in the All list are live for the chip that's picked, shown in either view because the tab reads the All list on every visit. Under the switch is the league filter (`FilterBar`, without Everything / Teams / Players). F1's and the UFC's chips replace the switch with views of their own (below).

**My games, step by step.**

- The server decides which games are yours: `deviceTeams` in `server/src/scores.ts` takes every team the device follows, plus the team of every player it follows, unless that player's "Show their team's games" switch is off (`playerTeams[playerKey].scores === false` in prefs). Any F1 follow (a driver or a constructor) adds every F1 session. The answer is cached for 5 seconds per device and dropped on every follow, unfollow (`forgetDeviceTeams` in `PUT`/`DELETE /me/follows/:key`) and `playerTeams` change in `PUT /me/prefs`, so the tab changes at once.
- `gamesFor` keeps the cards that involve one of those teams and are in the window (`inWindow`): live, or starting within 24 hours, or final for less than 24 hours (`KEEP_FINALS_MS`). It sorts live first, then upcoming (soonest first), then finals (newest start first).
- The app shows them in three sections, "Live now", "Later today" and "Final" (`SECTION` in `app/src/lib/scores.ts`), each with its count ("Live now · 2"), filtered by the league chip. The app applies the same 24-hour window on its own clock (`inWindow` in `app/src/lib/scores.ts`, re-checked every tick of `useNow`), so a final drops off even while the tab stays open.
- Every game shows, so both halves of a doubleheader are there. ESPN's note ("Doubleheader - Game 1 - Makeup from May 23") becomes the card's `note`, "Game 1", and the status line starts with it: "Game 1 · Final", "Game 2 · 7:05 PM" (`statusLine`).
- A final from a day before today says which day: "Final · Yesterday", or the weekday ("Final · Sun") (`dayLabel`).
- Then "Up next" (below). On a day with no games for the chip, that list is the whole screen, under a line in the chip's word: "No NFL games today.", or "No events today." with All. The line is left out when the first Up next game is today: a game tonight can be in Up next before ESPN's scoreboard turns over to the new day.
- With nothing at all: tracking nobody shows "Nobody to hate yet" with a "Find someone to hate" button that opens Search; tracking only F1 (or the F1 chip) shows the F1 message (below); otherwise "No NHL games today" ("No events today" with All), "When a team you track, or a player's team, plays today, the game shows up here with the live score."

**All games.** `GET /me/scores/all` returns `allGames()`: every card the server holds that is live, or upcoming and starting within 24 hours, tracked or not (finals are left out). It's sorted live first, then upcoming, then by league in the server's league order (`LEAGUE_IDS`: NBA, MLB, NFL, NHL, F1, EPL, UFC, CFB, with the WNBA always last), then by start. The app groups them the same way, live by league, then upcoming by league, under headers like "NBA · 3 live" and "NHL · 10 upcoming", in the league chips' order. The server only pushes a game to devices that track a side, so while All games is open (or the F1 chip is on) the app re-reads the list every 15 seconds (`ALL_GAMES_MS`), and for any game you do track it uses the store's socket-fed copy, which is fresher. A game that went final since the last read drops off. Tapping a game opens its game screen, tracked or not. Empty, in the chip's word: "No NBA games today", "Every game that's live or starts in the next 24 hours shows up here, whether you track anyone in it or not." (with All: "No events today", "Every event that's live…").

**A card, top to bottom** (`GameCardView` in `app/src/components/GameCard.tsx`):

- **The two teams**, away first. Each row has the logo and the short name (both open the team's page; VoiceOver offers "Open the Falcons page" as an action on the card), "Tracking" next to a team you track, the names of tracked players on a side you only track through them ("Bryce Harper"), and the score. A side you don't track, and the side that lost a final, have their name or score dimmed. College football teams in the top 25 carry their rank in the name ("#8 Indiana", `rankOf`; ESPN's 99 means unranked).
- **The status line**: the start time before a game ("8:15 PM" today, "Tue 8:15 PM" otherwise), ESPN's short status while live ("Q4 - 2:14", "Bot 8th"), and for football the ball and the down ("Q3 - 4:12 · ATL ball, 3rd & 8 at NO 41").
- **MLB's bases, outs and count** next to the status line: a diamond with the occupied bases filled, two out lights, and the count ("2-1").
- **The status pill**, from the hater's side (`hateTag`). Only when exactly one side is yours: hating both sides of a game gets no pill.
  - "Down 7" (red): good news.
  - "Threatening" (amber): the team you hate is in a spot to score: in football, in the red zone with the ball; in MLB, batting with a runner on second or third.
  - "Up 3" or "Tied" (grey).
  - Finals: "Successful Hate Watch!" (green) when they lost, "They won" or "Tie" (grey) otherwise.
- **"N other hate watchers"** under a final that gave you a Successful Hate Watch (see the counter section): `withHateWatch` in `server/src/hate-watches.ts` adds `hateWatch.alsoGot` to this device's copy of the card. Score frames over the socket are everyone's copy, so the app keeps its own count on the card when they arrive (`frame.kind === 'score'` in `app/src/lib/store.tsx`).
- **Live details** (`LiveDetails`), names of players you track in red:
  - **MLB:** "Pitching: S. Armstrong, 6 pitches" and "At bat: M. Murakami, 1 for 3, RBI, K". The pitcher, batter, their lines and the count come from the scoreboard's `situation`, which leaves them out between innings ("Mid 5th", "End 4th": nobody is batting then). ESPN's batter line "1-3" reads "1 for 3". Pitches thrown come from the summary's box score that the 2-second tracker already reads ("PC", or the first half of "PC-ST", `boxPitchCounts`), matched to the current pitcher's id, so a pitching change shows the new pitcher's own count. When there's no pitch count, and always on the game screen, the pitcher's line follows ("0.1 IP, 0 ER, 0 H, 0 BB").
  - **NBA, WNBA:** "Top scorers: T. Jerome 10 pts · N. Alexander-Walker 12 pts", from each competitor's `leaders` on the scoreboard (`leader`).
  - **NFL, college football:** "Timeouts left: ATL 3 · NO 3" while live, from `situation`, and the passer for the team with the ball ("Passing: T. Shough, 0/1, 0 YDS"; "1 TD" and "1 INT" are added once there are any). The game screen shows both passers. Once a game kicks off the scoreboard only names one passing leader for the whole game, so each side's passer (whoever has the most attempts) comes from the box score the tracker reads (`boxPassers`). The card keeps it through the final.
  - **NHL:** "Shots on goal: OTT 6 · BOS 3" and "In net: L. Ullmark (3 saves on 3) · J. Swayman (4 saves on 6)". The scoreboard only has each team's saves, so a side's shots on goal are the other side's saves plus its own goals. The goalie and their saves come from the box score (`boxGoalies`): the goalie the tracker has in net, so a change shows the new one, or else the last goalie the box lists. Scoreboard reads don't carry goalies, so the card keeps the last ones through the final.
  - **Soccer:** "Shots on target: LIV 3 · BOU 2" and, once anyone's been sent off, "Red cards 🟥 IPS 1 · EVE 0", from the scoreboard's statistics and match details.
  - **Every league but MLB:** "Last play: …" while live: ESPN's text for the latest play, skipping "Start of …", "End of …" and "Official Timeout". In soccer it's the latest goal or card with its minute ("Last play: 63' Own Goal: L. Martínez").
- **Before the start, a preview** (`gamePreview` in `server/src/scores.ts`, from the same scoreboard read, no extra requests):
  - Each team's record under its name, with the home side's record at home and the away side's on the road ("84-78 · 48-33 at home", "85-77 · 44-37 away"). A 0-0 record isn't shown, so a team before its first game has none.
  - Its chance to win where the score will go, under one "Win %" label at the top of the card. The chances come from the moneyline with the bookmaker's margin taken out (`lineChances`): each price's implied chance (a price of -115 is 115/215, +380 is 100/480, "EVEN" is 50%), divided by their total, rounded to whole percents, with the favourite taking any rounding leftover so they add up to 100. CLE -115 / CHW -104 is 51% / 49%; DAL -500 / TB +380 is 80% / 20%; a soccer line of -260 / +700 with the draw at +400 is 69% / 12% and a 19% draw. With no price for one side there are no chances.
  - Under the card: "Probable pitchers: P. Messick (0-1, 4.15 ERA) · H. Smith (0-0, 1.42 ERA)" in MLB, "Probable goalies" in the NHL ("TBD" for a side ESPN hasn't named); the line and over/under with whose it is ("Odds (DraftKings): CLE -115 · O/U 7", plus "Draw 19%" in soccer); soccer's form ("Form: LIV LWWWW · BOU WDLWW"); and a playoff series ("CHW lead series 2-1").
  - A card with nothing to say (a preseason game with no line and 0-0 records) has no preview.
- **"Chance the Guardians lose"** with a bar, when you track one side (`loseChance`): live, it's 1 minus ESPN's win probability for that side, where ESPN publishes it; before the start, the other side's chance from the line (in soccer a draw isn't a loss, so it's only the other side's win). Win probability comes from the scoreboard's last play and from the summary the 2-second tracker reads (`patchGame`), rounded to a tenth of a percent so float noise doesn't count as a change.
- **The newest alert from that game** at the bottom, its emoji, title and how long ago, from the feed (`latest` in `scores.tsx`).
- Finals are drawn a little faded.

**F1 on the Scores tab.** A session card (race, sprint or qualifying, `raceCard`) shows the session ("Singapore GP · Race"), its status ("Lap 56", "Final"), the flag when it isn't green as a pill ("Safety car"; a red flag is drawn as good news), a lap bar ("Lap 56 of 62", newer servers), and for each driver you track (or both cars of a constructor you track) their place, then their places since the start, gap to the leader and stops ("▲10 from P19 · +1:24.603 · 1 stop", `fromGrid` and `stopsText`), or how they went out ("Retired, lap 7"). Any F1 follow shows every session. With the F1 chip on, the switch is "Live races | Upcoming races" instead: Live races is what's running, then finals from the last 24 hours; Upcoming races is the weekend's qualifying, sprint and race still to come (practice isn't shown), each a card once the server has it and otherwise a row with its day and time that opens the weekend's preview, with the grid under a sprint or race once ESPN has set it ("Grid set after Qualifying." until then), and a "Preview the weekend" link on top. With no race live: "No race live right now", "Next: Qualifying, Sat 9:00 AM."

**F1 with nothing on** (the F1 chip, or All when every follow is F1): "No F1 sessions today", then "Next race weekend: Singapore Airlines Singapore Grand Prix, Oct 9–11." (or "The … is this weekend. Practice isn't shown here." once the weekend has started), then which sessions show up, with a "Preview the weekend" button (and "Find someone to hate" when you track no F1 driver or constructor). Between weekends ESPN's F1 scoreboard still shows the last one, so the next one comes from its calendar: `setF1Calendar` keeps every weekend's name, dates and event id, and `nextF1Weekend` is the first one that hasn't ended.

**The UFC on the Scores tab.** With the UFC chip on, the tab reads `GET /ufc/cards` every 30 seconds while it's open. "All fights" is the next card (with a link to its preview, its name, date and venue, each segment's fights under a header with the segment's name, start time and broadcast), then "Coming up", the card after. "My fights" is the fights of the fighters you track on either card. A fight opens the card with that fight on top.

**Up next.** Under today's games, each tracked team's next game that isn't already a card on the tab, soonest first (`UpNextRow` in `app/src/components/UpNextRow.tsx`), one row each.

- The title puts the tracked team first: "Falcons vs Ravens" at home, "Hawks at Spurs" away. Two tracked teams in one game are one row, away at home: "Saints at Falcons".
- Under it, the league tag and, joined by " · ": who you track on that team if it's only through players ("Tracking Patrick Mahomes"), what kind of game it is ("ALDS Game 3", "NLDS Game 4 · if necessary", "Preseason") and the national TV channel ("NBC", "TBS").
- On the right, the day and the time: "Today", "Tomorrow", a weekday within a week ("Sun"), or the date past that ("Oct 18"); and the time, or "Time TBA" before ESPN sets one (`upNextWhen`).
- Tapping a row opens the tracked team's page. The list follows the league chip, drops a game more than an hour past its start, and a team with nothing scheduled (its season is over) has no row.
- **Where it comes from** (`server/src/upnext.ts`): each tracked team's ESPN schedule (`/teams/{id}/schedule`; soccer adds `?fixture=true`, since its plain schedule lists results). The next game is the first one that hasn't started and starts no more than an hour ago (`nextFromSchedule`). A schedule covers one part of the season, so when that part has nothing left (the last preseason game is played) the regular season's (`?seasontype=2`) and then the postseason's (`?seasontype=3`) are read (`fetchNext`). The round and "if necessary" come from the schedule's note ("ALDS - Game 4 If Necessary" becomes "ALDS Game 4 · if necessary"), and a preseason game with no note says "Preseason". TV is the national broadcast, else the first one listed.
- **When it's read:** per team, not per device, so ten devices tracking the Yankees cost one read. A loop checks every minute (`startUpNext`) for teams that were never read or were read 3 hours ago (`HW_UPNEXT_REFRESH_MS`), four at a time; a follow kicks it at once, and a follow that comes during a read gets another read right after. When a team's game ends its entry is dropped (`staleUpNext`), since its next game is a different one now. Only teams in the game leagues are read (not F1 constructors or the UFC). NHL schedules are the biggest, about 1 MB a team.
- `GET /me/scores` carries it as `upNext` (`upNextFor`: the device's teams' next games, one per game, soonest first). Older app builds ignore it.

**The game screen** (`app/src/app/game/[key].tsx`), opened by tapping any card:

- The card on top, larger, with the extra lines (both passers, the pitcher's line). It stays live from the socket, and the screen re-reads the server every 15 seconds while the game is live; pull to refresh reads it at once.
- Two tabs: **Box score** (`BoxScoreView`, tracked players marked; "The box score shows up here once it starts." before the game) and **Highlights** (ESPN's clips and the game's key plays, including the plays that sent you alerts; "Highlights show up here once it starts."). ESPN's clips can be switched off on the server (`clips.highlights` in `server/src/flags.ts`).
- F1: a running order instead ("Running order", or "Results" after), with each car's gap to the leader and to the car ahead, places since the start and stops (`RaceOrder.tsx`), in the timing's order while it runs; before the session starts, the weekend's preview.
- Then "Your alerts from this game · 4" ("this race" in F1, "this fight" in the UFC), your alerts from that game, newest first, joined live by ones that arrive over the socket. Tapping the heading minimizes it, and the choice is kept on the device for every game screen (`game:alertsOpen` in AsyncStorage). With none: "Nothing yet. When something goes wrong for them, it lands here."
- A game the server no longer has (it's off the scoreboard and past its day): "This game isn't available", "Games stay on the Scores tab until the day after they finish."

**Where the data comes from** (`server/src/scores.ts`, `server/src/live.ts`):

- **The scoreboard read.** The live engine reads every game league's ESPN scoreboard every 10 seconds (`HW_SCOREBOARD_MS`; college football every 20 seconds, and only every 5 minutes when no game is live or starting within 20 minutes), F1's every 30 seconds. Every game on it becomes a card (`gameCard`; F1 sessions `raceCard`), whether anyone tracks it or not, stored in memory by key (`<league>:<ESPN event id>`; F1 `f1:<session id>`) through `upsertGame`.
- **The 2-second tracker.** For a game someone tracks, the tracker's play-by-play runs ahead of the scoreboard, so it patches in the score, win probability, MLB pitch counts, NHL goalies and NFL passers as it reads them (`patchGame`). While a game is live each side's score only goes up, so a stale scoreboard read can't undo a run the feed already announced; the final read is exact. NHL goalies and NFL passers are kept through the final, since scoreboard reads don't carry them.
- **When a final ended.** The server records `endedAt` when it sees a game go final. For one already over the first time it's seen (after a restart, or from yesterday's scoreboard), it uses a typical game length after the start (`GAME_LENGTH_MS`: MLB 3h, NFL 3¼h, college football 3½h, NBA 2¼h, WNBA 2h, NHL 2½h, soccer 2h, F1 2h; capped at now).
- **Yesterday's games.** ESPN's scoreboard rolls over to the new day, and a restart forgets what the server had seen. So every 10 minutes (`HW_YESTERDAY_MS`) it also reads each league's scoreboard for yesterday (ESPN's date, US Eastern) and adds the finals it doesn't have (`scanYesterday`). Games are forgotten (`pruneGames`) once they're off the scoreboard, a day and a half past their start, and off the tab.
- **Live.** Any change is pushed as `{ kind: 'score', game }` over the WebSocket, only to connected devices that track a side (`broadcast` with `deviceTeams`). A change means the card's JSON differs from the last one sent. The first sighting of a game (after a restart) is a baseline, not a push.

**API:**

- `GET /me/scores` → `{ games, nextF1, upNext }`: the device's cards (with `hateWatch.alsoGot` on finals that gave it a Successful Hate Watch), the F1 weekend that's on or else the next one (`{ name, startsAt, endsAt, eventId }`), and Up next. The app reads it when the tab is focused, on pull to refresh, on every socket (re)connect, and after every follow or unfollow.
- `GET /me/scores/all` → `{ games }`: All games, with the same per-device `hateWatch`.
- `GET /me/games/<league:id>` → `{ game, alerts, plays, box, clips, keyPlays }`: the card, the device's alerts from that game (by `events.game_id`; F1 alerts store their session id there; up to 100, newest first), and from one read of ESPN's summary, cached 8 seconds while live and 5 minutes otherwise (`gameDetail`): the box score, the clips (empty when `clips.highlights` is off), the device's key plays (`forDevice`), and `plays`, the latest 25 plays newest first (MLB at-bat results only, NFL drives flattened, soccer its key events) for builds from before the Highlights tab. 404 for a game the server doesn't have. If ESPN fails, the card and alerts still come back.
- Feed items carry `gameId`, so the app links alerts to their game.

**Checked:** live against CHW @ CLE on 2026-10-05 (the card, the losing chance with the Guardians 25% to lose, a pushed update at the top of the 6th, the game screen's play-by-play), and MEM @ ATL, OTT @ BOS and ATL @ NO for the other sports' lines. `server/test/scores.test.ts` covers the cards from real scoreboard events, scores that never go backwards, which devices get a change, each device's games, the MLB at-bat lines, the other sports' live details, F1 cards and calendar, the play-by-play, finals and doubleheaders, All games and the preview (the CLE @ CHW ALDS Game 4 scoreboard of 2026-10-08); `server/test/upnext.test.ts` covers Up next.

## Stats pages

**In short:** Every player and team page opens on a **Stats** tab (next to "Recent misery"): a player's season line, postseason and career, their last five games and their team's next game; a team's record and standing, its season line (the EPL's league table instead), its last five results and its next game; F1 drivers and constructors their championship season, and UFC fighters their record. The numbers worth gloating about (strikeouts, interceptions, errors, cards) are in red when there are any, and in a team's form an L is the green one. The server builds each page from ESPN at `GET /targets/:key/stats` (`server/src/stats.ts`) and keeps it for 10 minutes.

**Where it shows.** A player's or team's page (`app/src/app/target/[key].tsx`, opened from Search, the Tracking tab, a roster, the leaderboard, a game card's team or an alert) has two tabs under the name, the hater count and the Track button: **Stats**, which opens first, and **Recent misery** (your alerts about them from the last 24 hours). The stats are fetched alongside the page. If ESPN doesn't answer, the tab says "Couldn't load the stats. ESPN didn't answer." with "Try again". A team's roster, with its position chips, follows under both tabs. The same stats also have a screen of their own, `app/src/app/stats/[key].tsx` (titled "NYY stats"), kept for links that still open it; nothing in the app links there now. Both draw `StatsView` (`app/src/components/StatsView.tsx`).

**What's on a page, top to bottom:**

- **Record** (teams, and UFC fighters): the overall record, large ("93-68"), ESPN's standing summary under it ("2nd in AL East"), and the splits ESPN has ("Home 46-34 · Road 47-34"; "Away" where ESPN calls it that).
- **Stat groups**, each a heading and a grid of tiles. A tile is the number, ESPN's short label ("SO"), and what it means ("Strikeouts"). A tile marked bad is drawn in red with a red-tinted frame.
- **"Last 5 games"** ("Last 5 races" in F1, "Last 5 fights" in the UFC; "Last 3 games" when there are only three). A team's section starts with its form, oldest to newest, as round chips: an L is green (a Successful Hate Watch), a W plain, a tie or draw grey. Then one row per game: the date ("Oct 6"), "vs" or "@", the opponent's logo and code, and the result and score ("L 2-5"), the L in green. A player's row adds their line in that game under it.
- **"Next game"** ("Next race", "Next fight"): the same row as the Scores tab's Up next ("Yankees vs Rays · ALDS Game 3 · TBS", the day and time), which opens the team's page.
- A footer: "Stats from ESPN, updated every 10 minutes. In red: the numbers worth gloating about." A page with no record, groups or games says "No stats yet", "ESPN doesn't have numbers for them this season."

**Players** (`playerPage`), from ESPN's athlete overview (`site.web.api.espn.com/apis/common/v3/sports/<sport>/<league>/athletes/{id}/overview`):

- **The season line ESPN picks for their position:** a hitter's average and strikeouts, a pitcher's innings and earned runs, a quarterback's yards and interceptions; a goalie's save percentage; a soccer player's goals, cards and fouls. The group is the overview's "Regular Season" split, titled "Regular season". Soccer splits a player's stats by competition, so it's the league's own one, matched by its full name in `leagues.ts` ("2026-27 English Premier League"), or else the first split that isn't career or projected.
- **MLB hitters:** the overview has only their career line, so the season row comes from the athlete stats endpoint (`…/athletes/{id}/stats`): the latest season of its first category, titled "2026 season". That second read happens only when the overview has no regular-season split, and never for soccer.
- **Postseason** and **Career**, when ESPN has them, with the same columns.
- **The last five games**, from the overview's game log: date, home or away, opponent and logo, W/L/T/D, score, and the player's line in that game. The line is up to 10 of their numbers, and zeros after the first are left out, as are words like "Started": Aaron Judge's 2-0 win over the Mets reads "3 AB · 3 SO", his 8-3 win at Minnesota "4 AB · 1 R · 1 H · 1 HR · 3 RBI · 2 SO".
- **Next game:** their team's (`nextGameOf` in `server/src/upnext.ts`: the Up next entry if the server has a fresh one, else a read of the team's schedule now).
- **In red** (`BAD` and `badFor` in `server/src/stats.ts`), only when there are some (`some`: 0 isn't red):
  - MLB hitters: strikeouts, caught stealing, grounded into double plays.
  - MLB pitchers (positions P, SP, RP): earned runs, homers allowed, walks, losses, blown saves. A pitcher's strikeouts are his good number, so they stay white.
  - NFL quarterbacks: interceptions, sacks, fumbles, fumbles lost. Other NFL players: fumbles and fumbles lost.
  - NBA and WNBA: turnovers, fouls (totals and per game), technical and flagrant fouls.
  - NHL skaters: penalty minutes, giveaways. Goalies: goals against, goals against average, losses, overtime losses.
  - Soccer: fouls committed, yellow and red cards, own goals, offsides, goals conceded.
- Real example (`server/test/stats.test.ts`): Aaron Judge's page is "2026 season: GP 66 · HR 18 · SO 85 · CS 0 · AVG .241" with the 85 strikeouts red and 0 caught stealing not, then "Career: GP 1211 · AB 4342 · H 1262 · HR 386 · SO 1454". Gerrit Cole's "Regular season: IP 127.0 · ER 51 · HR 22 · K 131" has ER and HR red and his 131 strikeouts white.

**Teams** (`teamPage`), from ESPN's team (`/teams/{id}`), team statistics (`/teams/{id}/statistics`), standings and schedule endpoints, read in parallel:

- **Record and standing:** the team's total record, `standingSummary`, and its home and road splits.
- **The season line, picked per league** (`TEAM_STATS`), each tile ESPN's code on top and our words under it (where our words are the code itself, "ERA", ESPN's own: "Earned Run Average"):
  - MLB: batting average, runs, home runs, OPS, strikeouts (red), ERA, WHIP, errors (red).
  - NFL and college football (whose statistics use the NFL's names): points per game, yards per game, interceptions thrown (red), giveaways (red), turnover margin, sacks taken (red), penalties (red), 3rd down %.
  - NBA and WNBA: points, FG%, 3P%, rebounds, assists, turnovers (red) and fouls (red), the counting ones per game.
  - NHL: goals, goals against (red), save %, shooting %, power play goals, penalty minutes (red), +/-.
  - It's titled with the part of the season ESPN has: "2026 Postseason" or "2026 regular season". A real example: the Yankees in the 2026 postseason, "Batting avg .246 · Strikeouts 33 · ERA 1.32 · Errors 0", with the 33 strikeouts red and no errors not.
- **Soccer:** ESPN has no team stat line, so the EPL's is its table (`tableGroup`, from the standings), "League table": POS, PTS, P, W-D-L, GF, GA (red when any) and GD. Example: "POS 6th · PTS 9 · P 5 · W-D-L 2-3-0 · GF 7 · GA 4 · GD +3".
- **The last five results** (`recentFromSchedule`): the schedule's finished games, newest first ("@ TB L 2-5", "@ TB L 0-1", "vs TB W 9-0"). A game without a score (postponed) is skipped; a level score is T, or D in soccer, whose plain schedule is its results.
- **Next game:** `nextGameOf`, as above.

**F1** (`server/src/f1-stats.ts`): a driver's page is their points and place in the championship, wins, podiums, poles, DNFs, average finish and races ahead of their teammate (the other car that day), then their last five races ("Oct 4 · Monaco GP · DNF", a DNF or no points drawn like a loss). A constructor's is the same for both cars, with one-twos and double DNFs. DNFs and losing to the teammate are the red ones. It reads the championship standings, the season scoreboard (every session's finishing order) and each finished race's cars once (kept in `kv`). F1 rows have no "vs" or "@" and no form chips.

**The UFC** (`fighterPage` in `server/src/ufc.ts`): the fighter's record ("Record": W, L in red, KO W, SUB W, KO L and SUB L in red, from ESPN's records), and their last five fights from the overview's fight history, each with the opponent, W or L, how it ended (with the round, except for a decision), and ESPN's description. No next fight. The UFC's placeholder team has no page.

**API:** `GET /targets/:key/stats` (public, no device token) → `{ key, kind, league, record?, groups: [{ title, tiles: [{ label, name, value, bad? }] }], recent: [{ id, date, home, opponent, opponentLogo?, result, score, line? }], next }`. 404 for a key the catalog doesn't know, a league that doesn't exist, or the UFC's placeholder team (`statsFor`). Each page is cached for 10 minutes (`TTL_MS`), so a busy page is one set of ESPN reads every 10 minutes; up to 500 pages are kept, and a failed read isn't kept, so the next request tries again. ESPN reads time out after 8 to 10 seconds; a failed statistics or schedule read leaves that part out rather than failing the page.

## Successful Hate Watch counter

**In short:** The top of Settings counts the device's Successful Hate Watches, each time a team it tracks loses (or the team of a player it tracks), with the teams that gave it the most. The server counts them in `publish()` (`server/src/hate-watches.ts`) for every device the loss is addressed to, whatever its alert settings, once per device and loss, and sends the new tally over the WebSocket. Every Successful Hate Watch alert also says how many other people got it ("23 other hate watchers"). Clearing the feed keeps the count; "Delete all my data" removes it.

**What you see** (`app/src/components/HateWatchCounter.tsx`, the first card in Settings):

- The total, large and red, then "Successful Hate Watch" or "Successful Hate Watches", and under it "Each time a team you track lost." (or, at 0, "Your first one lands when a team you track loses."). While it's loading the number is "–".
- Up to three chips for the teams that gave it the most, each with the logo, the short name and the count: "Falcons 4 · Hawks 3 · Guardians 2". F1 constructors show their full names there, since ESPN's F1 short names are junk (Ferrari is "JK").
- With more than three teams, a "+2 more" chip. Tapping it expands the card into every team it has hate watched, most first, one row each with the logo, full name, league tag and count; "Show less" folds it back. The change animates.

**What counts** (`HATE_WATCH_TYPES` and `isHateWatch`):

- `team.lost`: a team you track loses ("Successful Hate Watch! Eagles lost to the Bears"). That includes an elimination and a blowout, which are the loss with other words; an alert that counts as a loss through its aliases counts too.
- `player.team_lost`: the team of a player you track loses ("Successful Hate Watch! Freddie Freeman and the Dodgers lost to the Giants").
- `<soccer league>.team.heavy_loss`: a 3+ goal loss ("Coventry were thrashed 5-0 by Brighton"), sent instead of the plain loss to those who want it.
- `f1.team.no_points`: your constructor finishes outside the points, and `f1.team.double_dnf` (a double DNF), which is also a no-points finish.
- `ufc.lost`: a fighter you track loses.
- Draws and ties send no loss, so they never count.

**Counted under the team, once per loss** (`hateWatchOf`). A player's "their team lost" and soccer's 3+ goal loss carry the team loss's own event id (`meta.lostId`) and the team's key (`meta.teamKey`), and are recorded under those. (The loss's other facts sent in its place, like "lost as 78% favorites" from `lossFacts`, carry `lostId` too but aren't recorded themselves; the loss alongside them already counted for every tracker.) So tracking Freddie Freeman puts the Dodgers on the list, never Freeman, and tracking the Dodgers and Freeman (or Freeman and Mookie Betts) counts one loss once. The table `hate_watches` has one row per device and event id (`ON CONFLICT DO NOTHING`), so re-polls and restarts never count twice. The UFC is the exception: `ufc.lost` is about the fighter, so a fighter you track appears on the list under their own name.

**When it's counted** (`publish()` in `server/src/fanout.ts`). Right after a new alert is stored, for every device it's addressed to (everyone tracking its target, plus, for a team's alert, anyone tracking one of its players with "Get their team's alerts" on), a Successful Hate Watch adds a row, before the device's alert settings are checked. So turning "Loses a game" or "Their team loses" off doesn't stop the count, and neither does the type's league switch. Each device whose count went up gets `{ kind: 'hateWatches', tally }` on its open sockets at once. A device that tracks nobody involved isn't counted.

**Taken back.** When an alert's facts change after it went out (an F1 result a penalty changed, `reviseEvent`), and it's withdrawn or no longer a Successful Hate Watch, its rows are deleted and each device that had one gets its new tally.

**Kept and reset.** Settings → Clear feed doesn't touch the count (the rows aren't feed rows). "Delete all my data" (`DELETE /me`) does: `hate_watches` rows cascade with the device.

**"23 other hate watchers."** Every Successful Hate Watch alert says how many other people got it in their feed: on the Feed card, on the alert's own screen, and on the game's final on the Scores tab ("1 other hate watcher", "0 other hate watchers"; `AlsoGot` in `app/src/components/ui.tsx`).

- It's `alsoGot` on the feed item (`feedItem` in `fanout.ts`): the alert's recipients minus you, only for a loss alert (`isLossAlert`: a Successful Hate Watch type, or an alert carrying `lostId`; not one that was withdrawn).
- Read from the database, it's the `RECIPIENTS` column: for a loss with a game, the number of different devices that got any loss alert from that game and league, the team's or a player's (each device gets one); otherwise the alert's own feed rows (indexed by `feed_event`).
- It's settled when the alert goes out: `publish()` works out who gets each alert before sending any, and adds up a loss moment's deliveries across its alerts, so the live alert carries the number too.
- On the Scores tab, `withHateWatch` adds `hateWatch: { alsoGot }` to this device's copy of a final that gave it a Successful Hate Watch, and the app keeps it on the card when everyone's score frames update the game.
- People with the loss alert off don't get the alert, so they don't count in it and don't see a number (though their counter still went up).
- Example (`server/test/hate-watches.test.ts`): three devices track an NFL team and one has "Loses a game" off. The loss counts for all three; the two that got it each see "1 other hate watcher"; the one with it off sees no number on the final.

**Losses from before the counter.** On the first start with it, the server counted the `team.lost`, `f1.team.no_points` and `f1.team.double_dnf` alerts already in each feed, plus the ones that happened while a device tracked the team (followed before the loss was detected) but never reached its feed because the alert was off. A `kv` flag (`hate_watches_backfilled`) makes this run once. Players' "their team lost" came later and is only counted as it happens.

**API:** `GET /me/hate-watches` → `{ total, teams: [{ target, count }] }`, most first (ties: the most recent loss first). The app reads it every time its socket connects, and takes each `hateWatches` frame as it comes.

**Checked** in `server/test/hate-watches.test.ts`: losses from before the counter (in a feed, and with the alert off; not one from before the device tracked the team), a loss counting for every tracker with the alert on or off, once, with one `hateWatches` frame; the winners not counting; the "others" count live, from the feed, and on the Scores tab; clearing the feed keeping the count; an F1 constructor out of the points and a double DNF counting while a game start doesn't; and "Delete all my data" taking the count with it.

## Leaderboard

**In short:** The podium button at the top left of every tab opens the most hated athletes and teams, ranked by how many people (devices) track them, filtered like the Feed: Everything, Teams or Players, in every sport or one league. Each filter is the top 100 ranked on the server within that filter, with 🥇🥈🥉 for the top three, ties shown as "T-2" with no gaps after them, and a note when the list is cut. It comes from `GET /leaderboard` (`server/src/leaderboard.ts`), public because it's only counts, never who.

**Opening it.** Every tab's header has a podium icon at the top left (`app/src/app/(tabs)/_layout.tsx`), instead of a sixth tab. It pushes `app/src/app/leaderboard.tsx`, titled "Leaderboard", with a Back button.

**The filter** (`FilterBar`, the same as the Feed and Tracking tabs, in the same words):

- **Everything / Teams / Players.** The third reads "Athletes" with All, "Players" in a league, "Drivers" in F1 and "Fighters" in the UFC (`playersTitle`, from each league's `ui.players`). The UFC has only fighters and college football only teams (`ui.kinds` in `server/src/leagues.ts`), so with those chips there's no choice to make.
- **The league chips:** All, then the leagues you track, then More (every league, by sport). "All" is the global board: Everything with All is every athlete and team in every sport, Teams with All is every team in every league.
- **Ranks count only what the filter shows**, so with MLB players picked the most hated MLB player is 1st, even if he's 40th overall.

**A row:** the rank, the photo or logo, the name with "Tracking" if you track them, the league tag and their subtitle, and the count on the right ("12 haters", "1 hater"). Tapping a row opens their page. Above the list: "Ranked by how many people track them on Hate Watch."

**Ranks and ties** (`leaderboard()`):

- Sorted by haters, most first; ties are listed by name (alphabetically).
- Ties share a rank, and the next count is the next rank with no gap: 1, T-2, T-2, 3 (the 3rd most hated count, not the 4th entry).
- The top three ranks get 🥇🥈🥉 instead of a number; a tie there shows "T-2" under the medal.
- The server flags a tie (`tied`) over the whole filtered list, not just the 100 it sends, so the 100th entry still reads as tied when the other half of the tie didn't fit.

**The top 100.** Each filter shows at most 100 entries, whatever a client asks for (`LEADERBOARD_MAX`; `limit` is clamped to 1–100). When there are more, the list ends with "Showing the top 100 of 224." If the 100th place falls inside a tie, it adds how many tied with it didn't fit: "124 more are also tied for 13th with 1 hater." Ties are listed by name, so that cut is alphabetical.

**Accuracy.** Each filter is ranked on the server from its own list, never by filtering the global top 100, so a league's board reaches its 100th entry even when the global board stops sooner. `server/test/leaderboard.test.ts` checks every filter (3 kinds × every league and All) against a brute-force count of a few thousand random follows, and that no request gets more than 100. On 2026-10-07 every filter on production matched a fresh count from its database. Switching filters quickly can't leave the wrong board up: each load is numbered and only the latest request's reply is shown, and the list clears while the new one loads.

**When it loads:** each time the screen is opened or comes back into view (so follows made elsewhere show), on every filter change, and on pull to refresh.

**Empty and failed:** "Nobody hates any NBA players yet", "Track someone and they'll show up here.", with "Show everything" when a filter is on (else "Find someone to hate", which opens Search). If the server doesn't answer: "Couldn't load the leaderboard" with "Try again".

**API:** `GET /leaderboard?kind=team|player&league=nfl&limit=100` → `{ entries: [{ rank, tied, haters, target }], total, moreTied }`. `total` is everyone in the filtered list; `moreTied` is how many tied with the last entry shown were left out. A `kind` other than `team` or `player`, or an unknown league, is a 400. It's counted live from `follows` with one grouped query: target keys are `kind:league:id`, so each filter is a key prefix (`team:nfl:%`, or `team:%` and `player:%` for Everything). A follow shows at once. A target that has left the catalog is dropped.

Tracking tab, "Fine-tune one player or team": a drawing of Daniel Jones' row, then what's next to everyone you track: the hater count ("How many people hate them, you included."), the bell (no notifications about just them; their alerts still reach the feed) and the gear (pick exactly which alerts you get about them, which beats the global settings).

**Moving through it:** swipe sideways (pages snap), or tap Next at the bottom. From the second page a Back link at the top left goes to the previous one. Skip at the top right closes it from any page but the last. Dots under the pages show where you are. The last page's button is "Find someone to hate" on the first run (it closes the guide and opens Search) and "Done" when rewatched (back to Settings). The pictures are drawings of the real controls, not live ones, so nothing in the guide changes settings.

**Once per install** (`app/src/lib/guide.ts`):

- On launch the root layout (`app/src/app/_layout.tsx`) asks `needsGuide()`, once the navigator is ready. If `hatewatch.guideSeen` isn't in AsyncStorage, it opens `/guide?first=1`; otherwise it settles the guide at once. A storage error counts as seen: better no guide than a stuck one.
- The guide marks itself seen (the time) as soon as it opens, so quitting the app halfway through doesn't bring it back next launch.
- Deleting the app clears AsyncStorage, so a reinstall shows it again.
- It's a full-screen modal with a fade, and it can't be swiped down; Skip, Done or the last button close it.

**Rewatch:** Settings → About → "Show the guide" ("How tracking and alerts work") opens `/guide` without `first=1`: no notification line on the last page, and the last button says Done and returns to Settings.

**Notification permission waits for it:** `guideSettled` is a promise that resolves when the guide closes (finished or skipped), or at once on a launch that doesn't show it. The store awaits it before `registerForPush()`, so on first launch the system prompt comes right after the guide instead of covering it. The last page warns that the prompt is coming.

**Small screens:** each page scrolls vertically on its own if it doesn't fit (small phones, large text sizes). It's checked on iPhone SE (375×667) and 390×844.

## An alert on its own screen

**In short:** A card in a list shows three lines of an alert's text; tapping it opens the alert on its own screen (`app/src/app/alert/[id].tsx`) with all of its text, its clip, how many other hate watchers got it, when it happened, who it's about and a Share button. The screen shows the feed's copy when there is one, so a line added later appears live, and otherwise the copy that was tapped. A developer notice opens the same way, from Hate Watch, with no page to open and nothing to share.

**Where it opens from:** any alert card (`FeedCard`): the Feed, a game's "Your alerts from this game", a player's or team's "Recent misery", and a shared alert's screen. The card shows the title and three lines of the body; tapping it calls `openAlert` (`app/src/lib/alerts.ts`), which remembers the tapped alert in memory and opens `/alert/<id>` (the id URL-encoded, and decoded again on the screen, as is if it can't be).

**What's on it, top to bottom:**

- The header "Alert", with Back.
- **Who it's about:** a row with their photo or logo, name and subtitle and a chevron, which opens their player or team page, as the card's photo does. A target that has left the catalog has no row. A developer notice shows the app's icon, "Hate Watch" and "From the developer" instead, and doesn't open anything.
- **The title** with the alert's emoji, and **the whole body**, every line of it, including lines added after it went out. Both can be selected and copied.
- **"N other hate watchers"** on a Successful Hate Watch (see the counter section).
- **When:** the league tag (not on a notice), the alert type's name, and the date and time ("Sat, Oct 11, 4:05 PM"), with "(2h ago)" when it's less than a day old.
- **Its clip**, when it has one (`AlertClip`).

**Which copy it shows:** the feed's copy of that alert when the feed has it, so a fact that comes later (an `eventUpdate` frame that adds a line) shows up live on the open screen; otherwise the one that was tapped (`openedAlert`), which covers alerts from a game screen, a player's page or a share link that aren't in the loaded feed. An alert in neither (a link to an alert that was cleared, after the app restarted) says "This alert isn't in your feed anymore." with "Go to your feed"; while the app is still loading it shows a spinner instead.

## Developer notices

**In short:** A developer notice is a message from Hate Watch itself that goes into every install's feed and is never pushed, for an emergency (an outage, alerts that went out wrong) or news of what's coming. It's sent from a shell on the server with `server/src/notice-cli.ts`, which writes it straight into the database (the work is in `server/src/notices.ts`), and the running server shows it in open apps within about 5 seconds. The same command lists notices and withdraws one; nothing in Settings turns them off, and only the user decides when one goes out (CLAUDE.md, "Release flow").

**What sending one does** (`sendNotice` in `notices.ts`), in one database transaction:

- One row in `events`: id `notice:<the time sent, in ms since 1970>`, type `app.notice` (`NOTICE_TYPE` in `fanout.ts`), league `news` (no league's, so it shows under All), target `app:hatewatch`, the title and body trimmed, `meta` `{"urgent":true}` or `{}`, and a share code like any alert.
- A feed row for **every device there is at that moment**, `pushed` 0 (`INSERT … SELECT … FROM devices`). A device registered later doesn't get it.
- `notices:latest` in `kv`: the id and time, for the running server to pass to open apps.
- No push, ever. A notice doesn't go through `publish()`, so prefs, mutes, quiet hours and the alert bells never apply to it, and nothing calls the push sender (`test/notices.test.ts` checks that no push is sent). It's the one exception to "every alert goes through `publish`" in [docs/duplicate-alerts.md](docs/duplicate-alerts.md), Layer 2: its feed rows still use `ON CONFLICT DO NOTHING`.

**How it reaches open apps.** `watchNotices()`, started at boot in `index.ts`, checks `notices:latest` every 5 seconds (`HW_NOTICE_POLL_MS`). When it changes, the server sends an `event` frame, the same shape as a live alert (`feedItem`), to every connected device whose feed has the notice, and logs `[notice] <id> sent live to the open apps of <n> devices: <title>`. Everyone else sees it the next time the app loads its feed (opening the app, reconnecting, pull to refresh). Two limits follow from watching only the latest:

- Two notices sent within 5 seconds of each other: only the second goes out live; the first appears on the next feed load.
- A notice sent while the server is down, or just before a restart, isn't sent live: the server starts from whatever `notices:latest` says at boot.

**How it looks** (`FeedCard.tsx`, `alert/[id].tsx`, `isNotice` in `app/src/lib/alerts.ts`):

- **Builds from the next one:** the app's icon (`AppAvatar`), the title, three lines of the body, and the label "From Hate Watch" with a megaphone emoji, the card edged in red (`colors.hateDim`). An urgent notice reads "Important: from Hate Watch" with a warning-sign emoji, edged in amber (`colors.warn`). The emoji and labels come from the server (`noticeLook` in `fanout.ts`). There's no league tag and no Share button, and the icon opens no page. Tapping it opens all of it on its own screen, from "Hate Watch, From the developer", again without Share.
- **Builds before:** the sender is team-shaped (`NOTICE_SENDER` in `fanout.ts`: a team called Hate Watch, abbreviation HW, colour `#E5232B`, logo `badge://hatewatch`), so every build draws it as a red "HW" badge, as it does F1's constructors, and nothing crashes on it; it carries a NEWS tag (its league) and the same label. Build 12 opens an empty page when it's tapped.
- **Where it doesn't count:** the weekly recap leaves notices out (`recap.ts`), and they're never a Successful Hate Watch. Settings → Clear feed deletes them with the rest of the feed, and "Delete all my data" removes them with the device.

**The command** (`notice-cli.ts`), run on the server's machine:

```bash
fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts"                                    # the latest 20, newest first
fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts send 'Title' 'Body' --dry-run"       # how many it would reach; sends nothing
fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts send 'Title' 'Body'"                 # send it (--urgent: marked important)
fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts send --b64 <base64 JSON>"            # the same, for text with quotes in it
fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts withdraw notice:<ms>"                  # take one back out of every feed
```

- **Which database.** `HW_DB` if set, else `/data/hatewatch.db` when it exists (the Fly volume), else `data/hatewatch.db`. It prints `database /data/hatewatch.db (<n> devices)` first, so a wrong database shows at once.
- **`send "Title" "Body"`.** Prints `sent notice:<ms> to <n> devices, feed only` and then the notice as sent (`urgent "Title": Body` when urgent). `--dry-run` prints `would reach <n> devices (nothing sent)` and writes nothing. `--urgent` and `--dry-run` can go anywhere after `send`.
- **`send --b64 <base64>`.** The base64 of `{"title","body","urgent"}` in UTF-8. `fly ssh console -C` passes one word whole, and base64 keeps quotes, apostrophes and emoji intact. It's urgent if the JSON says so or `--urgent` is given. Make it with `printf '%s' '<json>' | base64 | tr -d '\n'` (GNU base64 wraps long lines; the `tr` removes the breaks). For example, `{"title":"Live scores are delayed","body":"ESPN is slow tonight; alerts may come a minute late.","urgent":false}` is `eyJ0aXRsZSI6IkxpdmUgc2NvcmVzIGFyZSBkZWxheWVkIiwiYm9keSI6IkVTUE4gaXMgc2xvdyB0b25pZ2h0OyBhbGVydHMgbWF5IGNvbWUgYSBtaW51dGUgbGF0ZS4iLCJ1cmdlbnQiOmZhbHNlfQ==`.
- **Its checks** (`noticeProblem`): a title and a body that aren't blank, and a title of 120 characters at most ("the title is 131 characters; keep it to 120 (the rest goes in the body)"). The body has no limit, but the feed card shows three lines of it. A notice that fails a check prints the problem and the usage line and exits with status 1, sending nothing.
- **The list** (no command): the latest 20 notices, newest first, each as `<id>  <time, UTC>Z  <n> feeds[ URGENT]  "<title>": <body>`, where feeds is how many feeds still have it. With none: `no notices sent yet`.
- **`withdraw <id>`.** Deletes the notice's feed rows and its event, and prints `withdrew <id> from <n> feeds`. It only touches notices: any other id, or one already withdrawn, prints `no notice <id>`. An app that has it on screen keeps it until it next loads its feed. There's no live frame for a withdrawal.
- Any other command prints the usage line and exits with status 1.

**Before sending one** (CLAUDE.md): only when the user asks, with its exact title and body, and whether it's urgent, confirmed first, since it goes to everyone. Check the reach with `--dry-run`, then send it with `--b64`. A deploy that includes `notice-cli.ts` has to be live first.

**Tests** (`test/notices.test.ts`): a notice goes into every feed, never pushed, drawn as from Hate Watch (team-shaped with a `badge://` logo, league `news`); an urgent one says so; a dry run reaches no one, and the title and body checks; the weekly recap doesn't count notices; open apps get a new notice within seconds, and only those whose feed has it (a socket for a device created after it gets nothing); a notice is withdrawn from every feed, and `withdraw` refuses an id that isn't a notice.

## Sharing an alert

**In short:** Sharing an alert sends a link, `https://hate-watch-api.fly.dev/a/<code>`, not text. In Messages, WhatsApp, Discord, X and Slack the link previews as a 1200×630 picture of the alert that the server draws from its own data, so it looks like a screenshot. On an iPhone with Hate Watch installed, tapping it opens the app on that alert (a universal link); without the app it goes to the App Store; anywhere else it's a web page with the card and a download button. The code is the first 11 characters of a SHA-256 of the alert's id (`shareCode()` in `server/src/db.ts`), and the server side is `server/src/share.ts`.

**Sharing, step by step** (`app/src/lib/share.ts`):

1. Tap the share icon on an alert card (`FeedCard`), or "Share this alert" on the alert's own screen. Developer notices have no share button.
2. Every feed item carries `shareUrl` (`feedItem` in `server/src/fanout.ts`: `HW_PUBLIC_URL`, default `https://hate-watch-api.fly.dev`, plus `/a/<code>`).
3. On iOS (and in a browser with a share sheet) the share sheet gets just the URL, so Messages shows one bubble: the card. Android's share sheet only takes text, so it gets "<emoji> <title>", a new line, and the link. If an alert has no `shareUrl` (an old server), it shares the text instead: the emoji and title, the body, and "via Hate Watch" with the app's devil emoji.
4. The sheet is titled "Share this alert", with the alert's title as the subject (email).
5. A browser with no share sheet copies the text to the clipboard instead, and the button says "Copied" for 2 seconds. Cancelling a share does nothing.

**The code** (`shareCode()`): the first 11 characters of the base64url SHA-256 of the alert's id, so the same alert always has the same link. It's stored in `events.share_code` and indexed (`events_share`). Alerts from before share links got theirs when the server started (`db.ts` fills in any missing ones at boot). A developer notice gets one too.

**`GET /a/<code>`** (`shareLink`):

- **An iPhone, iPad or iPod** (by user agent) that isn't a link-preview bot gets a 302 to the App Store (`HW_APP_STORE_URL`, default `https://apps.apple.com/app/id6819054268`), whether or not the code exists, uncached and varying on user agent. With the app installed iOS never asks the server: it opens the app (below).
- **Everyone else, including link-preview fetchers**, gets an HTML page (`sharePage` in `server/src/pages.ts`). Messages fetches previews as "facebookexternalhit … Twitterbot" and must never get the redirect, so anything whose user agent matches bot, crawl, spider, facebookexternalhit, preview, slack, discord, whatsapp, telegram or embed gets the page. The page has:
  - Open Graph tags (`og:title` the alert's title, `og:description` its body, `og:url`, `og:site_name` "Hate Watch", and `og:image` the card at `/a/<code>/card.png` with its type, 1200×630 size and alt text) and Twitter's (`summary_large_image`, `twitter:title`, `twitter:image`), so the preview is the card at full width.
  - Apple's Smart App Banner (`apple-itunes-app`, the app id taken from the store link).
  - The card as an image, a "Download Hate Watch on the App Store" button, and one sentence about the app.
  - Cached 5 minutes. A `HEAD` request is answered like `GET`, for preview fetchers that check first. Page and card URLs use the host the request came to (and `x-forwarded-proto`).
- **An unknown code** gets the same page with status 404, the title "This alert isn't available" and no image (or the App Store, on an iPhone).

**`GET /a/<code>/card.png`** (`shareCard`): the card, drawn on the server from our own alert data with `satori` (layout to SVG) and `@resvg/resvg-js` (SVG to PNG). No user uploads, so no user-generated content to moderate.

- 1200×630, the size link previews show large. A near-black background with a red glow at the top.
- Top: a red dot and "HATE WATCH" on the left; the league ("NFL", "EPL") in a pill on the right ("NEWS" for a developer notice).
- Middle: a 168-pixel circle in the team's colour (a player's team colour; dark grey without one) with the team's code or the player's initials ("FF" for Freddie Freeman; Jr., Sr., II, III and IV are skipped), its text black or white, whichever reads on that colour. Team colours and initials, not ESPN logos or headshots: their images aren't ours to spread around. Next to it the title (cut to 110 characters, in one of three sizes by length) and the body (cut to 120, grey; a score like "LAD 0" doesn't break across lines).
- Bottom: the alert type's emoji and name, as in Settings, and a red "Get Hate Watch on the App Store" button.
- Text is Inter (500, 800 and 900 weights, from `@fontsource/inter`), with the Latin Extended subset so names like Dončić and Jokić draw. Emoji are Twemoji SVGs (16.0.1) fetched from jsDelivr, with a 3-second timeout and a blank space if one fails.
- Alerts never change, so cards are cached in memory (up to 300) and by HTTP for a day (`public, max-age=86400`). 404 for an unknown code.

**Opening the app (iOS universal links):**

- The app lists `applinks:hate-watch-api.fly.dev` in `ios.associatedDomains` (`app/app.json`), and the server's `/.well-known/apple-app-site-association` says app `G9V9266QK5.com.hatewatch.app` (`HW_IOS_APP_ID`: Apple Team ID plus bundle id) opens `/a/*` ("Shared alerts").
- iOS reads the association file (through Apple's CDN) when the app is installed or updated. If someone long-presses a link and picks "Open in Safari", iOS remembers that for the domain until they pick "Open in Hate Watch".
- Expo Router drops the domain and routes the path to `app/src/app/a/[code].tsx`. It fetches `GET /shared/<code>` (public: `{ item }`, the alert as a feed item, or 404) and shows the alert card, then "Get alerts like this about Freddie Freeman" with a Track button. A code that's gone says "This alert isn't available anymore." with "Go to your feed".
- The root layout's `unstable_settings.anchor = '(tabs)'` puts the tabs underneath, so Back works even on a cold start from a link.
- Android App Links aren't set up yet; they need `assetlinks.json` with the Play signing key fingerprint.

**Settings:** `HW_APP_STORE_URL` overrides the store link and `HW_PUBLIC_URL` the link's host. The App Store link only works once the app is released.

**Checked** in `server/test/share.test.ts`: feed items carry their link; an iPhone goes straight to the App Store; link previews get the page with the card as its image; the card is a 1200×630 PNG for teams and players, emoji and accents included; a developer notice shared from a build that still shows Share gets its page and card from Hate Watch; the association file names `/a/*` and the app can fetch the alert; and alerts from before share links get codes when the server starts.

## Tests

**In short:** `npm test` in `server/` runs every `test/*.test.ts` file with Node's own test runner: 314 tests in 49 files, offline, in about 4 seconds, all passing on October 11, 2026. Next to them are scripts that read live ESPN (replays of finished games, the two-feed check, an F1 replay, a catalog audit) and an end-to-end smoke test against a running server. On the Mac, recordings of live games under `server/data/recordings/` (not in git) are replayed through the real game tracker and checked against what production sent.

```bash
cd server
npm ci                        # once, on a fresh clone (not npm install: it can rewrite the lockfile)
npm test                      # every test/*.test.ts: 314 tests, offline, ~4s
node --test test/notices.test.ts   # one file
npm run typecheck             # tsc --noEmit

node test/verify-catalog.ts   # audits the ingested catalog: duplicates, images, logo fallbacks
node test/find-nobletiger.ts  # finds real NOBLETIGERs in recent MLB games
```

**How the unit tests run.** `npm test` is `node --disable-warning=ExperimentalWarning --test test/*.test.ts`. Node 22.18 or later (`engines` in `package.json`) runs the TypeScript files as they are, with no build step. Every test file sets `process.env.HW_DB = ':memory:'` before it imports server code (`db.ts` opens its file on import), so the tests never touch `server/data/hatewatch.db`; `share.test.ts` also builds a throwaway database in the system's temp folder to test the share-code migration, and deletes it. ESPN is faked through seams the live code reads from (`liveDeps.getJson` in `live.ts`, `f1Deps` in `f1.ts`), and the play shapes and wording are ESPN's own from real games, named in each file's header comment. ## Known limits

**In short:** Everything rests on ESPN's unofficial, undocumented API, so its delay is our floor and a change to its fields can break a league until the code catches up; the replays are the early warning. Some alerts are inferred rather than read (the NHL goalie in net, MLB runs charged to whoever is pitching), some leagues lack data ESPN doesn't publish (soccer injuries and streaks, F1 injuries), and some paths have only been tested on simulations or recordings. Each limit below says why it exists and what to do about it, where there's anything.

- **ESPN's API is undocumented and unofficial.** Field names, shapes and wording can change without notice, and nothing promises it stays up. *Why:* there's no official free feed for these leagues. *Workaround:* every test uses ESPN's real shapes and wording, and `node test/replay.ts` (finished games, tracked score against the final) is the canary; run it after anything looks off. The images and clips that lean on ESPN's rights can be switched off on the server without a build (`server/src/flags.ts`, CLAUDE.md "Release flow").
- **ESPN's delay is the floor.** A play reaches us when ESPN posts it, tens of seconds after it happens (see "Real-time"). *Workaround:* a lower-latency feed per league through the same `NPlay` interface, listed at the end of "Real-time".
- **The NHL goalie in net is inferred.** ESPN doesn't say who was in goal for each goal, so the tracker seeds each team's goalie from the box score when it first reads a game (`seedGoalies` in `live.ts`), then moves it to whoever makes each save, and to a goalie coming on as a substitute (`observePlay` in `detectors.ts`). An empty-net goal is nobody's: it gets no goalie alert, and the team that gave it up gets `nhl.team.empty_net_goal` ("… gave up an empty-netter to the …") instead.
- **MLB "gives up runs" goes to the pitcher on the mound for that play** (the play's `pitcher`), not by official earned-run or inherited-runner rules. A reliever who lets an inherited runner score gets the alert, though the run is charged to the man before him. *Workaround for what's official:* blown saves, no quality start and the loss are read from ESPN's box score (`boxPitchers`, `pitcherEvents`), which uses the official numbers.
- **Standings and injury alerts fire on change, and the first read is a silent baseline.** The last read is kept per league in the server's `kv` table (`standings:<league>`, `injuries:<league>`; `scanStandings`, `scanInjuries` in `live.ts`). A fresh database, a new server, or a newly added league starts with a baseline, so a change that happened before that first read never alerts. College football has no injury scan.
- **A restart forgets what the server only keeps in memory.** Football revisions of plays posted before a restart, late lines for alerts sent before it, and MLB holds (an ABS challenge, a half-inning's end) are lost; the database's ids still stop anything going out twice. The full list is in [docs/duplicate-alerts.md](docs/duplicate-alerts.md), "What survives a restart". *Workaround:* deploy when nothing is live.
- **F1's live path has only been tested on simulations and one recorded weekend.** In-race DNFs and double DNFs are tested with a simulated race through the real engine (`test/f1-live.test.ts`), and the timing (the running order's gaps, pit stops, lapped and places lost) the same way (`test/f1-timing.test.ts`). The timing was read from ESPN during the 2026 Singapore GP's last laps; ESPN only said "GREEN", then "CHECKER" at the end, so any other flag shows as ESPN words it, made readable ("SAFETY_CAR" is "Safety car"; `flagLabel` in `f1.ts`).
- **F1 sessions with alerts are qualifying, the sprint and the race** (`sessionKind` in `f1.ts`). Sprint qualifying (ESPN's "SS", the sprint shootout) and practice send none. F1 has no injury report on ESPN, so no F1 injury alerts.
- **Soccer has no injury alerts, no losing streaks and no elimination.** ESPN's EPL injury report is empty, the table carries no streak, and a league season has no playoff to be knocked out of (a drop into the relegation zone is its alert instead). "Loses the ball" and "Gives the ball away" are judged from the touch after (`soccerTouch`), since ESPN doesn't mark a pass or dribble as failed. A recording of Manchester City at Liverpool (October 11, 2026) is on the Mac for replaying them (`replay-epl.ts`); no soccer change has reached main since.
- **Clips exist only where ESPN has them:** MLB, the NBA, the WNBA and the NHL (`CLIP_LEAGUES` in `live.ts`; ESPN had none for the NFL or soccer in October 2026), plus a lost UFC fight's clip.
- **A developer notice reaches only the devices registered when it's sent,** and only the latest one goes out live (see "Developer notices").
