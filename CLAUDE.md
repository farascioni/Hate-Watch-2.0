# Hate Watch: working notes for Claude

## Index

**Summary:** the rules for working in this repo, short, because every session loads this file on every call. The explanations, files and examples behind each rule are in `docs/working-in-this-repo.md`; read the part you need there.

- **Read the docs first**: read an area's docs before changing it, and keep them current in the same commit; the docs' format; the three hooks.
- **Release flow**: ask before every commit, push or deploy; deploys (the Litestream replica and `/health/deep`: `docs/redundancy.md`), switches, notices, builds, updates, the league display, EAS's queue.
- **Don't run npx expo lint in app/**: typecheck only, and the lockfile check.
- **Patch notes**: every shipped change, under 4,000 characters, no emoji.
- **Two machines (Windows and Mac)**: setting up a machine, logins, what stays local, the Mac's game recorders.

The app is in `app/` (Expo, see `app/CLAUDE.md` and `app/AGENTS.md`), the server in `server/` (Node, SQLite, Fly.io). `README.md` is the map of how everything works.

## Read the docs first
Before planning or changing anything (a feature, a fix, an alert, its wording, a release step), read what the docs say about that area, and say in your plan which sections you read. The code does what they describe: a change that departs from them updates them in the same change (the README section, `PATCH_NOTES.md`).
- `README.md` is the map: an Index, then one short section per area ("In short") linking to its full detail in `docs/<topic>.md` (`run-it`, `deploy`, `data`, `real-time`, `notifications`, `scores-tab`, `stats-pages`, `hate-watch-counter`, `leaderboard`, `favorites`, `startup-guide`, `alert-screen`, `developer-notices`, `sharing`, `tests`, `post-game-recording-report` (the template for every recorded game's report), `known-limits`). Every alert in detail: `docs/alerts.md`. The UFC and college football: also `PATCH_NOTES.md` and the header comments of their modules (`ufc.ts`, `cfb-poll.ts` in `server/src`).
- **Read a doc's Index first, then only the sections you need** (the Read tool's offset and limit). Don't read whole long docs for a small change.
- This file for releasing: deploys, builds, over-the-air updates, patch notes, server switches, the two machines.
- `app/AGENTS.md` before touching any Expo or React Native API (fetch the versioned Expo docs), and `docs/` for store releases.
- `docs/duplicate-alerts.md` (the vault's "Duplicate alert protection") before every change to alert code, read in full again for each new instruction, even if you read it earlier in the session: how one thing happening stays one alert (deterministic ids, `publish()` storing an id once, the game tracker's memory, moments and folds, ESPN's edits, restarts). Its "Files this covers" lists the alert files; the hook below blocks an edit to one until it has been read since the latest user message.
- The module's own header comment: every file in `server/src` starts with what it does and why.
- On the Mac, the Hate Watch Obsidian vault (`~/Documents/obsidian/hate-watch`, start at `Home.md`) has all of this split by topic, with the game review reports and the standing decisions. It's a private copy; the repo wins where they differ. It rebuilds itself from GitHub's main (the README, this file, `PATCH_NOTES.md` and the commit log) when a session starts and after any git push, pull, fetch or merge (`.claude/settings.json`; nothing happens on a machine without it), so a change documented in the README is documented there too.
- Side sessions and subagents follow the same rule: a brief names the docs to read first.
- A hook enforces it (`.claude/settings.json` runs `.claude/hooks/require-docs.mjs`): an edit to `app/` or `server/` code (with the edit tools, or a shell command that writes to a code file; read-only commands pass) is blocked until the session has read `README.md`, `docs/`, an `AGENTS.md` or the vault, and the block says which docs cover that file. `HW_DOCS_GATE=off` in the environment turns it off for an emergency.
- **Update the docs with every change, in the same commit:** the README section and its `docs/` file, `docs/alerts.md` for an alert, `docs/duplicate-alerts.md` for a new kind of alert id, this file for a release step, the module's header comment, and `PATCH_NOTES.md` for a shipped change. On the Mac, the vault's log for the day lists the day's commits by itself (generated from git; a day with commits and no hand-written note gets one), and you add the story (decisions, deploys, what to check) as a bullet in that day's `note('80 Log/<date>', ...)` call in `.tools/build_vault.py`, then `sync.sh --force`; a third hook (below) reminds you after a commit, deploy or build. When nothing documented changed, the commit message says so: `Docs-unchanged: <why>`.
- **Every doc opens with an index:** `# Title`, then `## Index` as the first `##` heading (a `**Summary:**`, then every section with one line); the README's sections each open with `**In short:**`. Below the index: complete and checked against the code (files, functions, defaults, real examples), each fact once. A new subject gets its own `docs/<topic>.md`, and the README a short section linking to it. The vault indexes and imports these on its own.
- A second hook (`.claude/hooks/require-docs-update.mjs`, before every Bash call) stops a `git commit` that changes code without a doc or a `Docs-unchanged:` line, or whose README, CLAUDE.md or `docs/*.md` breaks the index format. Merges and test-only commits pass. `HW_DOCS_GATE=off` for an emergency.
- A third hook (`.claude/hooks/remind-vault-log.mjs`, after a Bash call that succeeded and is a `git commit`, `fly deploy`, `eas build`/`update`/`submit` or `npm run update`) records a deploy, build or update in the vault's log for the day by itself (`.tools/events.jsonl`, rendered as "Deploys and builds that day (generated)", then it rebuilds the vault) and tells the session to add the story as a bullet. It is installed in `.claude/settings.json` and in the user settings (`claude-config/settings.json`, copied to `~/.claude/settings.json` by `install.sh`), because a session in a git worktree reads that worktree's own copy of the project settings, which can predate the hook; a command that fires both is handled once, and a command outside this project's folders is ignored. It never blocks; `HW_LOG_REMINDER=off` silences it, and a machine without the vault gets nothing.

## Release flow
- After a change is built and tested, ask before you commit, push or deploy, every time. Don't do any of them unasked. The user wants a say before anything goes public or live, and Apple sign-in is theirs to do.
- Server: deploy from `server/` with `flyctl deploy --remote-only` (or `fly deploy --remote-only`). The app `hate-watch-api` runs on one machine with its SQLite database on a volume at `/data`. Before anything that changes production data, back it up with SQLite's `VACUUM INTO` into `/data`. The database is also streamed off the volume by Litestream once `LITESTREAM_REPLICA_URL` is set, and `GET /health/deep` is the outside monitor's check (`docs/redundancy.md`: setup, runbooks; `/health/deep` has been live since release v81 on October 13, 2026; replication has run since the 19:12 UTC restart that day; an UptimeRobot monitor calls it every 5 minutes and emails the owner). A secret change restarts the app, so use `fly secrets set --stage` and restart when nothing is live. (`--ha=false` was for the first deploy only, which created the one machine.)
- Server switches (`server/src/flags.ts`) turn off what leans on someone else's rights or service without a build: ESPN's video clips, `clips` (all), `clips.highlights`, `clips.feed`, `clips.loss` (and within it `clips.loss.ufc`, a lost UFC fight's clip); and its player photos and team logos, `images` (both), `images.headshots`, `images.logos` (every build then shows a badge in the team's colour with its code instead, `server/src/images.ts`). List or flip one, live within seconds: `fly ssh console -a hate-watch-api -C "node /app/src/flag-cli.ts clips.feed off"` (`on` to undo; it prints the database it opened, which should be `/data/hatewatch.db`). Apps drop a switched-off clip the next time they load the feed (opening the app, reconnecting, pull to refresh). To keep one off for good, `fly secrets set -a hate-watch-api HW_FLAGS_OFF=clips.feed` (restarts the app).
- Developer notices (a message from Hate Watch in every install's feed, never a push; README "Developer notices", `docs/developer-notices.md`): send one only when the user asks, with its exact title and body (and whether it's urgent) confirmed first, since it goes to everyone. Check the reach with `--dry-run`, then `fly ssh console -a hate-watch-api -C "node /app/src/notice-cli.ts send --b64 <base64 of {\"title\",\"body\",\"urgent\"}>"` (base64 keeps quotes and apostrophes intact). The same with no command lists them; `withdraw <id>` takes one back. It needs a deploy with notice-cli.ts first.
- App: changes reach people only in a new EAS build. Send one to TestFlight only when asked, from `app/`:
  `npx eas-cli@latest build --platform ios --profile production --auto-submit --non-interactive --no-wait`.
  `eas.json` has the App Store Connect app id and EAS stores the certificates, profile and API key, so it runs without an Apple login. The optional "TestFlight group setup" step needs one and is skipped, which is harmless. New entitlements would need an interactive build by the user.
- Before a build: a clean git tree, `npx tsc --noEmit` in `app/`, and the lockfile check below.
- App over the air (EAS Update, `expo-updates`): builds after build 12 take JavaScript and asset changes (screens, wording, styles) without TestFlight. Ask before publishing, as for a deploy. From `app/`, with a clean tree and `npx tsc --noEmit` passing: `npm run update -- --message "…"`. The script sets `EXPO_PUBLIC_API_URL` to production; release builds fall back to production's API anyway, never localhost. Phones download it in the background when the app opens and run it from the next launch (launch never waits: `fallbackToCacheTimeout` 0), so a tester force-quits and reopens up to twice. `runtimeVersion` uses the fingerprint policy: an update reaches only builds with the same native code, so a native change (a new native module, permissions, entitlements, an SDK upgrade) needs a build before its updates. To roll back: `npx eas-cli@latest update:rollback` (interactive: the previous update, or the build's own). Its changes go in `PATCH_NOTES.md` like any app change, noted "(Update)" once published. `preview` builds use the `preview` channel: the same command with `--channel preview --environment preview`. Never add such a command as a `package.json` script: the scripts are part of the fingerprint, and a new one stops updates reaching every build already out.
- How the app shows each league (its chip color, which filter options it offers, what its people and events are called, football's card lines, division sorting) is the server's: `ui` in `server/src/leagues.ts` LEAGUES, read by `app/src/lib/leagueUi.ts` (builds after build 12; this build's own values are the fallback). Change it there and deploy the server, no build.
- EAS's free tier can queue a submission for about 2 hours, one at a time per account. If Apple returns a 500 on "Creating Build Upload", resubmit with `npx eas-cli@latest submit --platform ios --id <buildId>`; don't rebuild. Progress: `eas build:view <id> --json` (its log files carry `"phase"` steps; RUN_FASTLANE is the Xcode compile) and `eas status --json`.

## Don't run `npx expo lint` in app/
ESLint isn't set up, so `expo lint` installs it and rewrites `package-lock.json`. Local npm 11 accepts that, but EAS Build's `npm ci` (npm 10) rejects it, which failed iOS build 3. EAS uploads uncommitted changes too, so it gets into a build unnoticed. Typecheck with `npx tsc --noEmit` only. Before an EAS build, check the lockfile with `npx -y npm@10.9.8 ci --ignore-scripts --dry-run` on a copy of `package.json` and `package-lock.json`. On a fresh clone, install with `npm ci`, not `npm install`, so the lockfile isn't rewritten.

## Patch notes
Keep `PATCH_NOTES.md` up to date with every shipped change, server changes too (written like any other, with no marker), under "Next build". When a TestFlight build is sent, rename that heading to the build number and date and start a new "Next build" above it; `eas build:list --json` gives each build's git commit. Each build's section is pasted as is into TestFlight's "What to Test", so it must be **under 4,000 characters** and **use no emoji**. Update it in the same change as the code, and check each section's length and that it has no emoji (a `\p{Extended_Pictographic}` regex) before committing.

## Two machines (Windows and Mac)
Both machines work from this repo, and neither needs the other turned on. Production runs on Fly and builds run on EAS.
- On a new machine, or after a `git pull`: `bash claude-config/install.sh` sets Claude Code's user settings, this file's notes and the two scouts to the repo's copies. Anything it replaces is kept beside it as `<name>.before-<time>`. Then `npm ci` in `app/` and in `server/`.
- Logins, once per machine: Claude Code itself, `npx eas-cli@latest login`, `fly auth login`, and GitHub for `git push`. GitHub takes a personal access token (classic, `repo` scope, from github.com/settings/tokens), not the account password: run `git push` in a terminal, give the username `farascioni` and paste the token as the password, and the keychain or credential manager keeps it.
- Not in git, so each machine keeps its own: `.claude/settings.local.json`, `app/.expo/`, `server/data/` (the dev database, which the server rebuilds from ESPN on first start), and Claude's memory under `~/.claude/projects/`. This file is the shared copy of the notes that matter.
- Game recorders (the Mac; `server/data/recordings/recorders.py`, not in git): a background task dies when the Claude app restarts, so start every recorder through the script's registry (`recorders.jsonl`), never as a session's own background task. A SessionStart hook in `.claude/settings.json` runs `recorders.py --restart` and puts each recorder's state in the session's context (a start, a resume and a context summary all fire it), so read that instead of running it again. The script relaunches the dead ones; you tell the user and the recorder's owner session about any it relaunched. Name a recording session by its game: title `<AWAY> at <HOME> <LEAGUE> recording` (ESPN abbreviations, e.g. `CLE at TB MLB recording`), short name `rec-<league>-<away>-<home>` (`rec-mlb-cle-tb`), started by the "Game recorders for tonight" session. A LaunchAgent (`com.hatewatch.recorders`) also runs `recorders.py --agent` every 5 minutes and at login, so recorders return after a reboot with no session open; any entry it relaunched shows "the background agent relaunched it ... tell <owner>" in the hook's output until you tell the owner and run `recorders.py --told <name>`.
